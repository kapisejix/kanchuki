## RC-078 — The WhatsApp enquiry text was built from different inputs on the server and client paths

- **Component:** `packages/shared/src/utils/index.ts` (`buildEnquiryMessage`), `apps/api/src/routes/public/public-collections.ts`, `apps/api/src/routes/public/public-my-style.ts`. Fixed 2026-10-22 (`446a0ec0`, PR #147, merge `707fa3a6`).
- **Symptom:** an enquiry sent through the API (wishlist basket, My Style) reached the retailer with no product link and no SKU, and My Style named the store twice: `I saw your collection "Radha Clothing Store" from Radha Clothing Store.`
- **Root cause:** one shared builder, but each caller chose its own inputs. The client paths passed `product_url`; the two API routes passed only name + price. My Style has no collection, so it passed the shop name as `collectionTitle`, and the builder always printed both.
- **Fix:** both API routes pass `sku` and `product_url` (`buildProductUrl`; My Style uses the `all-{store}` pseudo-slug the product page already resolves). The builder prints `(SKU: …)` after the price and drops the quoted title when it is missing or equals the shop name. `GET /public/products/:id` returns `sku`, so the single-product consent-modal path carries it too.
- **Proof:** `packages/shared/src/utils.test.ts` (SKU + link line, store named once for null/empty/same-as-shop titles), `public-collections-enquire.test.ts` (the route's wa.me text has the SKU and the `/shop/abc/product/a` link).
- **Follow-up (`e3b1ce64`, PR #149, merge `97cad538`):** the storefront bottom-bar "Enquire" (`CollectionView.handleEnquireAll`) still built its text client-side from summaries with no `sku`. It now POSTs saved picks to the enquire route like WishlistView. Category / All-products pseudo-slugs (`cat-{id}`, `all-{store}`), which the route 404'd, now resolve through the `store` the proxy adds and record against the store's oldest live collection.
- **Not verified / known gap:** no real WhatsApp send or device run. With nothing saved, or more than 20 picks (API cap), the bottom bar still falls back to the client-built link without SKU.

## RC-077 — Stored user text was placed into HTML (hrefs, JSON-LD, email bodies) with no escaping step

- **Component:** `apps/web/src/app/admin/{aggregators,retailers/[id],social}/page.tsx`, `apps/web/src/app/stores/page.tsx`, `apps/api/src/routes/retailers/retailers-aggregators.ts`, `apps/api/src/lib/email.ts`. Fixed 2026-10-22 (`dbb389bb`, PR #142, plus `fix/security-hardening-2`).
- **Symptom:** a retailer-controlled URL (e.g. `channel_shop_url`) could be `javascript:…` and rendered as an admin `href`; `/stores` JSON-LD could be closed early with `</script>`; team-member name/phone went raw into the welcome-email HTML. The no-API-key email fallback also logged the plain-text body (temp password / reset code) in every environment.
- **Root cause:** each surface interpolated stored strings straight into markup. There was no shared escaper and no scheme check, so safety depended on every author remembering it (same shape as RC-040).
- **Fix:** `safeHttpUrl()` (web) for every stored href, http(s) only; API rejects non-http(s) `channel_shop_url`; JSON-LD escapes `<`; `escapeHtml()` in `email.ts` applied to every interpolated value; the fallback logs the body only outside production.
- **Proof:** `apps/web/src/lib/safe-url.test.ts` (12), `apps/api/src/lib/email.test.ts` (hostile name/phone never reach the HTML raw).
- **Not verified:** no CSP yet (proposed, not applied), so a missed interpolation elsewhere would still execute.

## RC-076 — Payment callbacks granted access without verifying Razorpay's signature or the charge itself

- **Component:** `apps/api/src/routes/billing/billing-{helpers,addons,webhook}.ts`, `apps/api/src/routes/public/public-catalog-payment.ts`. Fixed 2026-10-22 (`dbb389bb`, PR #142).
- **Symptom:** a caller could post a payment-link / checkout callback with made-up ids and be credited; a `subscription.charged` webhook activated a plan for an authorized-only, non-INR or underpaid payment.
- **Root cause:** the callbacks trusted what the client (or the webhook body) said about the payment. No HMAC check existed on the callback paths, and an empty `RAZORPAY_KEY_SECRET` would have made any HMAC forgeable.
- **Fix:** `verifyPaymentLinkSignature` / `verifyOrderSignature` (fail closed on an empty secret or signature, constant-time compare); webhook requires `captured`, INR and amount >= base price; catalog payment re-fetches the payment from Razorpay and checks the exact amount.
- **Proof:** `billing-signatures.test.ts`, additions in `billing.test.ts`.
- **Not verified / known gaps:** no live Razorpay round trip. The legacy 2-part `link_id|payment_id` signature is still accepted. The webhook amount check is >= base, not exact base + GST.

## RC-075 — Upload "confirm" endpoints recorded whatever key, URL and bytes the client reported

- **Component:** `apps/api/src/lib/upload-guard.ts` (`verifyUpload`, `sniffUploadType`, `sniffImageType`), `packages/ai/src/r2.ts` (`inspectObject`). Fixed 2026-10-22 in `dbb389bb` (PR #142: product photos, variants, KYC, logo/banner) and `fix/security-hardening-2` (categories, bug-report screenshots, growth videos, retailer showcase designs, catalog-import bulk create, try-on photo, catalog upload-url) and `fix/admin-upload-verify` (admin studio styles, post templates, background images, admin showcase designs, design references, showcase watermark logo).
- **Symptom:** a retailer could save another retailer's R2 key or any external/`javascript:` URL as their own image; a PUT of HTML/SVG/EXE bytes to a presigned "image" URL was accepted; `/catalog-import/upload-url` signed any `content_type` (e.g. `text/html`) onto the public CDN; the try-on route accepted any `image/*` the client declared (HEIC, SVG). Admin side: studio-style / post-template thumbnails and background images stored the client's `*_url` as-is, and `POST /admin/background-images` then **fetched that URL server-side** for tone/naming (SSRF); admin showcase accepted any `showcase-designs/*` key (incl. other retailers' raw/final objects) to watermark and republish; design references took `image_url` + `r2_key` on trust; a new watermark logo key was composited onto every design without a byte check.
- **Root cause:** a presigned PUT fixes the key and the declared Content-Type but not the body, and every confirm route was hand-written to trust the client's `r2_key` / `*_url` instead of checking ownership and the stored bytes. Nothing shared enforced it, so each new upload flow repeated the gap.
- **Fix:** one `verifyUpload()` on every retailer confirm path: key under the caller's own prefix (no traversal), object exists, size cap, magic bytes in an allow-list (JPEG/PNG/WebP, PDF, MP4/MOV/WebM; HEIC/AVIF refused); a failing object is deleted; the stored URL is rebuilt server-side from the key. Admin confirm paths use the same `verifyUpload()` in prefix-only mode (no retailer): `admin/studio-styles/`, `admin/post-templates/`, `admin/background-images/`, `showcase-designs/global/raw/`, `admin/design-references/`, `showcase-watermark/logo/`; client `*_url`/`image_url` inputs were removed (admin web now sends the key). `isOwnedKey()` treats an empty prefix as owning nothing. Bare URLs must point at our CDN. Multipart photo routes (try-on, My Style) sniff bytes via the shared `sniffImageType`. Catalog upload-url content types are an allow-list. Mobile `compressImageForUpload` now re-encodes a small non-JPEG/PNG/WebP pick (HEIC) instead of passing it through.
- **Proof:** `upload-guard.test.ts` (18), `products-tryon.test.ts` (HEIC labelled image/jpeg → 422, nothing stored), `categories.test.ts` +3, `growth-videos.test.ts` +3, `retailers-showcase-designs.test.ts` +1, mobile `compress-image.test.ts` +1; admin: `upload-guard.test.ts` +2 (prefix-only mode, empty prefix), `admin-showcase-designs.test.ts` +2, `admin-settings-watermark.test.ts` +1, `admin-studio-styles.test.ts` +2, `admin-post-templates.test.ts` +2.
- **Not verified / known gaps:** nothing run against live R2 or a real device. Presigned PUTs cannot cap size (confirm deletes oversize objects after the fact). Uploads that are never confirmed stay in the bucket until an R2 lifecycle rule exists. Design references have no upload-url route or admin UI, so nothing mints `admin/design-references/` keys yet (the endpoint is unusable until one is added). Background-images and design-references have no route-level test. Web photo sheets (`accept="image/*"`) do not convert HEIC; Android Chrome may send one and gets a 422.

## RC-074 — `POST /try-on/discard` counted every repeated job id as "skipped"

- **Component:** `apps/api/src/routes/products/products-tryon.ts`. Fixed 2026-10-19 on `fix/f-044-tryon-cleanups`.
- **Symptom:** a discard request listing one id three times answered `skipped: 2` for a job that was found and discarded.
- **Root cause:** `skipped` was `job_ids.length - jobs.length`, comparing the raw request length with the number of distinct rows the `IN (...)` lookup returned.

- **Proof:** `products-tryon.test.ts` > "a repeated id is looked up once and does not inflate skipped".
- **Not verified:** the mobile client never sends duplicates today, so this was only reachable by a hand-built request.

## RC-073 — The try-on quota screen reported plan defaults and ignored in-flight jobs, so it disagreed with the server that enforces the limit

- **Component:** `apps/api/src/lib/quota.ts` (`getQuotaStatus`), `GET /v1/products/try-on/quota`. Fixed 2026-10-19 on `fix/f-044-tryon-cleanups`.
- **Symptom:** a retailer with no `TRY_ON_GENERATION` limit row, or an explicit unlimited (-1) row, saw a 0 / 30 / 100 allowance on the in-store try-on pre-flight (Starter: 0 left, blocked), while `POST /try-on` would have let every request through. A retailer with jobs already running saw a larger "remaining" than the POST would accept.
- **Root cause:** two functions answered the same question independently. `checkQuota` returns (allows) on no row or -1 and adds recent PENDING jobs to the request; `getQuotaStatus` instead substituted Growth 30 / Pro 100 plan defaults, invented `unlimited` from them, and never counted PENDING jobs. The defaults were written for Studio Shoot, not try-on (whose limits are 20 / 50 / 100).
- **Fix:** `getEnforcedQuota(retailerId, type, reserved)` mirrors `checkQuota` (no row / -1 = unlimited; remaining = limit - used - reserved), and the try-on route uses it with the same `pendingTryOns()` count the POST uses. `getQuotaStatus` is untouched: Studio Shoot and the scheduler still use it.
- **Proof:** `quota.test.ts` > `getEnforcedQuota` (unlimited cases asserted against `checkQuota` itself for all three plans; limited remaining with reserved), `products-tryon.test.ts` (reserved passed through, unlimited passed through).
- **Not verified:** the in-store screen was not re-run on a device. Studio Shoot still shows plan defaults when its limit is -1; left alone on purpose (the scheduler works around it).

## RC-072 — A try-on that finished after its consent was withdrawn lost the pointer to its image when the R2 delete failed

- **Component:** `apps/api/src/jobs/tryon.ts` (`handleTryOn`). Same shape as RC-044. Fixed 2026-10-19 on `fix/f-044-tryon-cleanups`.
- **Symptom:** after a shopper withdrew consent while the GPU was still working, the generated image was deleted in the job; if that delete failed the image stayed in R2 with no row pointing at it, so the hourly deletion sweep could never find it.
- **Root cause:** the in-job "record the key before deleting" write was added for DISCARDED in-store jobs only (`WHERE status = 'DISCARDED'`). For a withdrawn job it matched nothing, so on a failed delete the key was nowhere. The sweep keys on `consent_withdrawn_at` plus a `result_url`, which that row never got.
- **Fix:** the record write matches `status = 'DISCARDED' OR consent_withdrawn_at IS NOT NULL`, still only while `result_url` is null and never changing status. On success the pointer is cleared as before; on failure the sweep now owns it.
- **Proof:** `tryon.test.ts` > "withdrawn mid-run + failed delete: the key is recorded for the deletion sweep (RC-072)" (fails against the old handler), and the discard test pins the new `where`.
- **Not verified:** not run against a real R2 outage. A withdrawn job's `status` stays `PENDING` with a key on it; nothing serves that, but it is odd to see in the table.

## RC-071 — The add-on callback turned a failed Razorpay lookup into a terminal FAILED, so a customer who paid could never be credited

- **Component:** `apps/api/src/routes/billing/billing-addons.ts` (`GET /billing/addon-callback`). Found while closing the F-044 Release 2 known gaps; fixed 2026-10-19 on `fix/f-044-addon-callback`.
- **Symptom:** a retailer completes a try-on top-up payment, Razorpay's payment lookup times out or 5xxs at that moment, and the pack is never credited. Replaying the callback does nothing.
- **Root cause:** the callback verifies the HMAC signature (proof the link was paid through Razorpay), then fetches `/payments/:id`. The `catch` around that fetch wrote `FAILED`, and the callback only ever looks up `PENDING` rows, so a transient lookup error made the purchase permanently uncreditable. The same unguarded `update` (by id, no status check) was used for the amount-mismatch path, so a late duplicate callback could also overwrite a `COMPLETED` purchase with `FAILED`. And the separate "paid but the credit transaction failed" path stayed `PENDING` correctly but only wrote a log line, so nobody was told.
- **Fix:** a failed lookup, or a payment Razorpay has not captured yet (`authorized`), leaves the purchase `PENDING` and redirects to `status=error` so a replay can credit it. Only a definitive negative (wrong amount, or payment status `failed`) becomes `FAILED`, and that write is `updateMany ... WHERE status = 'PENDING'`. The lookup-error and credit-failure paths call `Sentry.captureException` (tags `addon-callback` / `addon-credit`).
- **Proof:** `billing-addons.test.ts` > "a paid purchase is never terminally lost (RC-071)" (lookup error, `authorized`, wrong amount, `failed`) and the credit-failure test now asserts the Sentry call. Mutation-checked: against the old handler 5 of these fail.
- **Not verified:** no real Razorpay round trip. Whether Razorpay Payment Links can reach `authorized` without auto-capture in this account is unknown; if one stays there forever the purchase stays `PENDING` until someone replays it or support credits it manually.

## RC-070 — The My Style occasion filter and Kids form sent quiz labels the ranker never matches

- **Component:** `apps/api/src/routes/public/public-my-style.ts` (`/feed`), `packages/shared/src/style-quiz.ts`. Found and fixed 2026-10-18 on `feat/f-045-tabs` (PR-10a), while wiring the Occasion tab.

## RC-069 — The occasion backfill skipped every NULL `occasions` row, so it reported "nothing to do" on a catalog that needed all of it

- **Component:** `apps/api/src/jobs/occasion-backfill.ts` (shipped in #127). Fixed 2026-10-18 on `fix/occasion-backfill-null`.
- **Symptom:** the owner's dry-run printed `scanned=0`, and `count(*) FILTER (WHERE cardinality(occasions)=0)` also returned 0 for 216 live AI-tagged products. Neither meant "already filled": `SELECT ... unnest(occasions)` returned no rows at all.
- **Root cause:** `products.occasions` is a nullable `TEXT[]` with no default (`000_baseline`: `"occasions" TEXT[]`), and nothing has written it since occasion was removed on 2026-08-10, so those rows are `NULL`, not `'{}'`. Prisma's `isEmpty: true` compiles to `= '{}'` and `cardinality(NULL)` is `NULL`, so every NULL row falls out of both the filter and the write re-check. The tests mocked Prisma and only ever fed it `[]`, so the NULL case was never exercised (same mock-agrees-with-code shape as RC-037).
- **Fix:** candidate ids come from raw SQL (`occasions IS NULL OR cardinality(occasions) = 0`), the row is then loaded by id, and the write is a raw `UPDATE ... WHERE id = ? AND (occasions IS NULL OR cardinality(occasions) = 0)` so a retailer edit or concurrent re-tag still wins. `tag-product` was never affected: it reads `current.occasions?.length ?? 0`.
- **Proof:** `occasion-backfill.test.ts` asserts the select and the write both contain `occasions IS NULL OR cardinality(occasions) = 0`, plus cursor paging, limit, dry-run, race (0 rows changed) and failure cases.
- **Not verified:** not run against the real DB after the fix. The owner re-runs the 30-product dry-run; it should now scan up to 30 of the 216 rows.

## RC-068 — Catalog-upload and support-session delegates could use (and burn quota on) the owner/manager-only try-on routes

- **Component:** `apps/api/src/routes/products/products-tryon.ts` (all four Bearer routes: `POST /:id/try-on`, `GET /:id/try-on/status`, `GET /try-on/quota`, `POST /try-on/discard`). Fixed 2026-10-17 on `feat/enquiry-r2-delegate-try-on-fix` (F-044 R2).
- **Symptom:** a delegated catalog-upload token (allowlist `* /v1/products`) or a support-session token (scope includes `/v1/products`) could start try-on generations, poll them and read the quota. Each generation spends the retailer's monthly `TRY_ON_GENERATION` allowance, and spec §5.4 says owner + manager only.
- **Root cause:** an "owner-only" rule was inferred from `request.staffRole`, but delegates also carry `staffRole = null` — the same sentinel a real owner has (`isRealOwner()` in `plugins/auth.ts` exists for exactly this). `POST /:id/try-on` had no role check at all, relying on the staff allowlist (which only constrains real Staff rows), and the two routes that did check hand-copied their own three-way test. Same shape as RC-034: one access rule, several hand-written copies, the copy that mattered missing.
- **Fix:** one helper `requireTryOnStaff(request)` (no retailer -> 404, `VIRTUAL_TRY_ON_V2` off -> 404, salesperson / catalog delegate / support delegate -> 403), called first on all four routes whenever the caller is a Bearer retailer (before any product lookup, so a refused caller learns nothing about products). The customer-cookie path is unchanged. Side effect, intended: the Bearer status poll now 404s when the flag is off, like the POST.
- **Proof:** `apps/api/src/routes/products-tryon.test.ts` > `RC-068` — for each of the 4 routes, catalog and support delegates get 403 with no product/job/quota read, delegate + flag off is 404, owner and manager pass; salesperson 403 on all. Failed first: 8 failures (POST try-on and status let delegates through).
- **Not verified:** no live delegate token exercised; no mobile flow calls these routes with a delegate token (grepped `apps/mobile`).

## RC-067 — wa.me links dropped the +91 country code for any 10-digit mobile starting with 91

- **Component:** `packages/shared/src/utils/index.ts` (`buildWhatsAppEnquiryLink`), plus two hand-copied builders: `apps/web/src/app/c/[slug]/components/DesignGallery.tsx` and `apps/api/src/routes/growth/growth-helpers.ts` (`buildWhatsAppDeepLink`). Fixed 2026-10-17 on `feat/enquiry-r1-t7-whatsapp-target` (F-044 E5).
- **Symptom:** a store or customer number like `9123456789` (valid Indian mobile) produced `wa.me/9123456789`, which WhatsApp reads as country code 91 + an 8-digit number. - **Not verified:** no device check.

## RC-062 — 13 daily/weekly maintenance crons were registered with BullMQ `repeat.limit: 1`, which caps the job to ONE run per API boot, so they silently stopped repeating

- **Component:** `apps/api/src/jobs/index.ts`. Found 2026-10-16 (Customer Engagement stayed at zero); fixed on `fix/cron-repeat-limit`.
- **Symptom:** Customer Engagement showed all zeros even after products were opened for days — the nightly `engagement-aggregate` rollup never produced rows. Same defect meant backups, purge, GST backfill, R2 compression, embedding backfill, catalog sync, referral qualify/accrue and try-on sweep ran only once after each deploy/restart.
- **Root cause:** `limit` in BullMQ is the *total number of repetitions* (`repeat.js`: `iterationCount > repeatOpts.limit` → stop scheduling the next job), not a per-run guard. With `limit: 1` the first scheduled run executes and no successor is ever scheduled; the next `add()` at boot schedules one more. ## RC-047 — The deploy pipeline had no signal for "the new revision is live": `railway up --detach` never reports a build outcome, and `verify-deploy` checked liveness of the public URL that the **incumbent** revision answers — so a failed build was reported as a successful deploy

- **Component:** `.github/workflows/deploy.yml` — `deploy-web`'s `railway up --detach --environment production` step and `verify-deploy`'s two `curl … || echo "⚠️ …"` checks. Compounded by the absence of branch protection on `main`. Found 2026-09-28 while verifying the F-037 §2 row 5 deploy, when the platform's own report and the platform's own logs disagreed about the same commit.
- **Symptom:** one push (`a90ad39e..aac12cce`, 10 commits) produced **two contradictory verdicts for the same commit `aac12cce`**:
  - **CI run `36416629488` → `quality` FAILURE.** `pnpm lint` → `@kanchuki/web#lint` → `next lint` → `./src/app/admin/engagement/page.tsx` `221:39` **`react/no-unescaped-entities`** — a bare apostrophe in JSX text → `ELIFECYCLE Command failed with exit code 1`. `e2e-web` and `build` were **skipped** (`needs: [quality]`), so the web build was never even attempted in CI.

## RC-045 — the passport proxy rebuilt every upstream response with `new NextResponse(body, { status })`, and a **null-body status may not carry a body** — so `204` threw, the catch reported an unreachable API, and every fire-and-forget passport write failed silently

- **Component:** `apps/web/src/app/api/passport/[...path]/route.ts` — the shared `forward()` helper (the `new NextResponse(body, …)` line). Found 2026-09-26 while teaching the customer e2e stub API to serve three routes it was 404ing, which is the only reason it was found at all.
- **Symptom:** `POST /v1/public/passport/events` (the behavioural beacon — favourite, unfavourite, enquiry) and `POST /v1/public/passport/recently-viewed` both answer **204** upstream (seven `reply.status(204).send()` sites in `apps/api/src/routes/public/passport/passport-activity.ts` — it is the route's "accepted, nothing to say" answer). The proxy converted that 204 into a **503**. The web's only caller of the beacon is fire-and-forget to a literal `.catch(() => {})` (`apps/web/src/lib/passport-client.ts`), so the event never arrived, nothing logged, and no test went red. **Effect: the F-037 Phase 1 web event beacon has never worked** — a shopper favouriting, unfavouriting or enquiring from the customer PWA produced no `CustomerEvent` row, and `POST /passport/recently-viewed` would have failed the same way for any client that used it (the web keeps recently-viewed in `localStorage` instead).
- **Root cause:** a status code's contract encoded in a constructor. `new Response(body, { status: 204 })` **throws** — 204, 205 and 304 are defined as *null-body* statuses, and passing one a body (even `''`) is a `TypeError`. That throw landed in the same `catch` the helper keeps for a genuinely unreachable upstream, so "the API deliberately answered no-content" and "the API could not be reached" became one 503. This is RC-032's shape one layer out: a deliberate throw met a boundary that had already decided what any throw means, and the comment above the code asserted the opposite of what it did.
- **Why 32 green tests did not catch it, which is the part worth keeping:** the 204 never existed anywhere in the test surface. The proxy's unit test mocks `fetch` and only ever resolved 200s (`new Response(JSON.stringify(…), { status: 200 })`); the e2e **stub** answered 404 for that path, so the proxy passed a 404 straight through and the console check dutifully failed on the *404* — the one status that never reaches the buggy line. The defect needed a 204 to be produced by the stub, which is exactly what fixing the e2e added. Both suites were green *and* the beacon was dead, for the same reason: nothing had ever put a null-body status through the forwarder.
- **Fix:** `const NULL_BODY_STATUS = new Set([204, 205, 304])` at module scope next to `PASSPORT_PATHS`, and `const body = NULL_BODY_STATUS.has(res.status) ? null : await res.text()`. Null rather than the (empty) text: for these statuses there is nothing to read, and the set states *why* the branch exists rather than special-casing `=== 204`.
- **Proof:** `apps/web/src/app/api/passport/[...path]/__tests__/route.test.ts` gained `describe.each([204, 205, 304])` — three cases, one per member of the set, each asserting the upstream status arrives intact. **Falsified:** reverting the single line turns all three red with `expected 503 to be 204` / `205` / `304` — the production symptom reproduced verbatim. End to end, the collection spec's stub now answers 204 for `POST /v1/public/passport/events` (matching the real API rather than inventing a shape that avoids the bug), and the full customer e2e suite went **32/32** from **28 passed / 4 failed**.
- **Adjacent defect found, recorded and NOT fixed here:** the same helper drops the query string — it fetches `${apiUrl}/v1/public/passport/${subpath}` and never forwards `request.nextUrl.search`, so `/api/passport/recently-viewed?limit=10` reaches the API with no `limit`. Latent rather than broken (the route has a default), and a different decision (whether the proxy should forward an arbitrary query to an allowlisted path at all) than the null-body fix, so it is written down rather than bundled in.
- **Verified:** web **424 passed** (was 421; +3), `tsc --noEmit` and `next lint` clean; customer e2e **32/32**; admin/dev e2e 28 passed with one **pre-existing, unrelated** failure (see below).
- **The pre-existing failure, stated so it is not mistaken for this fix's:** `playwright.config.ts` (the dev-server config) ignores only `**/customer-collection.spec.ts`, so it also runs `customer-my-stores.spec.ts` — including `the production build meets the installability prerequisites`, which asserts `navigator.serviceWorker.ready` reports an **active** worker. `next dev` ships no service worker (the config's own comment says so), and that test is at `HEAD` unchanged with `playwright.config.ts` untouched by this change, so it has been failing in the dev run independently. It passes in the production config. Left alone: the fix is a config decision (a production-only PWA assertion living in a spec the dev config runs), not a stub.

## RC-044 — a withdrawn try-on's image was deleted by two separate best-effort code paths and **neither left a durable record or a retry**, so a failed delete orphaned the object permanently while the row stopped saying anything was owed

- **Component:** `apps/api/src/lib/tryon-consent.ts` — `withdrawTryOnConsent()` (the inline R2 delete during withdrawal) and `apps/api/src/jobs/tryon.ts` — the completion write (~line 145). Found 2026-09-26 while working F-040's pre-launch list; the first half was the reported gap, the second was found in the job while fixing it.
- **Symptom:** the platform's deletion promise for a withdrawn try-on could go permanently unmet, silently. Two ways in, one state out. (1) `withdrawTryOnConsent()` stamps `consent_withdrawn_at` and deletes the stored image, but when that R2 delete fails it **cannot** clear `result_url` — that key is the only pointer to the object, so clearing it would make the row claim there was nothing left to remove while the object sat in the bucket forever. (2) A generation that finishes **after** its consent was withdrawn writes its result key into a window the withdrawal already swept: the job's completion write was an unconditional `prisma.tryOnJob.update({ … data: { status: 'COMPLETED', result_url: resultKey } })`, so a row that already carried `consent_withdrawn_at` was handed a fresh `result_url` — a stored photograph of someone who had withdrawn, on a row no reader ever consults again (the status route answers `withdrawn` before it looks at anything else), and that no code path would ever delete. Both leave the same terminal state: `consent_withdrawn_at IS NOT NULL` **and** `result_url IS NOT NULL`. Nothing logged, nothing threw, no test went red — the withdrawal returned success and the object simply stayed.
- **Root cause:** **the pointer and the promise were the same column, and nothing swept the state that results when they disagree.** The withdraw path had to keep `result_url` on a failed delete precisely because it is the delete's only handle — which means the failure path *necessarily* leaves a withdrawn row still holding a key, and that state had no reader, no retry, and no alert. The job's half is the mirror image: an unconditional write assumed the row was still consented, because the comment above it reasoned about consent being checked at *enqueue* time and never considered the 35–45 s the GPU takes, during which the row can change underneath it. The shared failure shape is the RC-030/RC-038 one — an operation that succeeds while doing nothing (here, a withdrawal that reports success while its deletion did not happen), made durable because the *record* of what is owed was erased by the same act that made it owed.
- **Fix, both halves:** (1) `withdrawTryOnConsent()` keeps its inline delete (a cleanup-that-runs-later would make the promise conditional on the job's health) and still leaves `result_url` in place when the delete fails — but that state is now **caught rather than terminal**: a new hourly job `apps/api/src/jobs/tryon-deletion-sweep.ts` (`handleTryOnDeletionSweep`, registered in `jobs/index.ts`) selects withdrawn rows that still carry a key, oldest first, and retries the delete. It only clears `result_url` **after** a successful delete (so the pointer is never dropped before the object is gone), never touches `consent_withdrawn_at` (the withdrawal is the audit record and must outlive the cleanup it triggered), and leaves the key for the next run on failure — logged as an unmet deletion promise rather than swallowed. (2) The completion write became conditional: `updateMany({ where: { id: job_id, consent_withdrawn_at: null }, … })` makes the consent check and the write **one statement**, so there is no gap between them for a withdrawal to land in; `count === 0` means it landed, and the job then deletes the key it had already written, best-effort. Both paths converge on the one sweep — it keys on the *state*, not on an error code, so it is the retry for a failed withdrawal delete and a failed post-withdrawal write alike.
- **Why one job and not two:** the two halves produce an identical row state and need an identical remedy, and a second job for the job-side half would be free to disagree about what "owed" means. The sweep is deliberately **not** a general R2 orphan cleaner — it only ever touches keys a `consent_withdrawn_at` row still points at, so it cannot delete an image whose owner is still consented. No index on the predicate, on purpose: `try_on_jobs` is one row per quota-capped generation, the query is hourly, and the partial index would cost a migration and a write-path change to speed up a scan that is already negligible.
- **Proof:** `apps/api/src/jobs/tryon-deletion-sweep.test.ts` and `apps/api/src/jobs/tryon.test.ts`. The sweep's predicates: deletes and then clears the key, **leaves the key when the delete fails** (and counts it `failed`, not `deleted`), never clears before the delete succeeds, does not touch `consent_withdrawn_at`, and selects only withdrawn rows carrying a key. The job's arm: a completion that lands on an already-withdrawn row deletes the key it wrote instead of attaching it. **Falsified 2 ways, each red on exactly its own assertion and restored:** (1) the sweep's predicate widened so it would clear `result_url` without a successful delete → its test red; (2) the job's `updateMany` condition removed back to the unconditional `update` → the withdrawn-completion test red. **Verified:** API **1525 passed / 5 skipped** (was 1517 before this batch), `tsc --noEmit` clean, `biome check src/jobs/` clean.
- **Still metered, deliberately:** a withdrawal that lands mid-run **still spends quota** — the GPU ran regardless, and not metering it would make withdraw-and-regenerate a free way to spend the store's allowance (`hasLiveTryOnConsent` lets a shopper re-grant, so that loop is reachable from the UI). Recorded in the job's comment so the next reader does not "fix" it.

## RC-040 — JSON-LD was injected with `JSON.stringify` into `dangerouslySetInnerHTML`, and `JSON.stringify` does not escape `<`, so a retailer's own `shop_name` could close the `<script>` tag and run markup on **every** storefront page (stored XSS)

- **Component:** `apps/web/src/app/[store]/lib/store-seo.ts` (`ldJson`) · consumers `apps/web/src/app/[store]/page.tsx`, `apps/web/src/app/[store]/categories/page.tsx` (both shipped with raw `JSON.stringify`), plus the new `[collection]` / `[collection]/product/[productId]` JSON-LD added by §7A.2 · found 2026-09-24 while working the launch-readiness board (§7A.2).
- **Commit:** fixed in this session. The store + categories pages had been shipping the unescaped form; the two other surfaces were caught before their first commit.
- **Symptom:** none that monitoring could see — the pages render correctly for every well-formed store, which is every store in production. The trigger is data, not code: a retailer whose `shop_name` (or a product name / category in the `ItemList`) contains `</script>` closes the JSON-LD script element, and everything after it is parsed as markup — `<script>alert(1)</script>` runs with the storefront's origin. Stored, because the value is saved once at onboarding and served to every visitor afterwards.
- **Root cause:** **`JSON.stringify` is a serialiser, not an HTML escaper, and `dangerouslySetInnerHTML` is an HTML sink.** The two were used together with no escaping step in between, which is safe for every value except the one that matters. `JSON.stringify` deliberately leaves `<`, `>`, `&` and `/` as-is (they are valid inside JSON strings), and the HTML parser does not know it is inside a JSON-LD block: it ends the script element at the first `</script`, **case-insensitively** — so `</SCRIPT>` and `</script >` break out too. This is the OWASP XSS-prevention rule for `application/ld+json` verbatim: JSON inside a `<script>` must have at least `<` escaped, and the conventional transform is `<` → `\u003c` (unambiguous in the document, identical after `JSON.parse`).
- **Why it survived review:** three locally-correct readings. The data is **our own** (a retailer's profile, not a visitor's input), so the annotation read as "trusted" — but the retailer is an untrusted principal relative to the storefront visitor; `RETAILER-INPUT → OUR PAGE → ANOTHER USER` is stored XSS by definition. The `biome-ignore lint/security/noDangerouslySetInnerHtml: JSON-LD from our own retailer data, no user input` comment **asserted safety where the check would have fired**: the lint rule was doing its job, and the suppression stated the opposite of the truth. And the output *looks* escaped — it is full of `\"` and `\\` — so nobody re-checks whether it also escaped `<`.
- **Fix:** one helper, `ldJson(data) = JSON.stringify(data).replace(/</g, String.raw`\u003c`)`, used by all four JSON-LD call sites (store, categories, collection `ItemList`, product `Product`/`Offer`). Escaping every `<` also covers `<script`/`<!--`; `>` and `&` are not needed here because only `<` can start the sequences that end a script element. The `biome-ignore` is kept — the sink is still a sink, and the data is now escaped rather than trusted.
- **A near-miss in the fix itself, and how it was caught:** the first written form was `.replace(/</g, '\u003c')` with **one** backslash, which in a JS string literal is the single character `<` — i.e. a no-op that replaced `<` with `<` and looked identical in the diff to the correct form. `store-seo.test.ts` was run before the change was committed and went **red** on exactly this, which is why the escape is now the `String.raw` template (a literal `\u003c`, no escape-processing layer in between) and the test asserts the **absence of `</script>` in the output string**, not merely that the page renders.
- **Proof:** `store-seo.test.ts` **3/3** — the escape arm asserts `out` does not contain `</script>` **and** `JSON.parse(out).name` still equals the original raw string (escaping must not change the value), plus Offer/AggregateOffer/no-offer and `ItemList` numbering. **Falsified:** reverting `ldJson` to bare `JSON.stringify` turns the escape arm red (`expected '…' not to contain '</script>'`), the two other arms stay green. Web **326/326**, `tsc --noEmit` clean.
- **Prevention lesson:** **every HTML sink needs its own escaping rule, and "our own data" is not one of them** — the trusted/untrusted boundary is *between principals* (retailer vs. visitor), not between the database and the page. The mechanical checks: a `dangerouslySetInnerHTML` on `<script type="application/ld+json">` must route through a helper that escapes `<`, and any suppression comment on that lint rule must name the **escaping function**, never the provenance of the data. Corollary from the near-miss: a security assertion that only checks the *rendered result* cannot see a no-op escape — assert the dangerous substring is **absent from the serialised string**, which is what makes a one-backslash mistake fail.

## RC-033 — The billing webhook collapses `subscription.completed` into `Subscription.status = CANCELLED`, so "finished its paid term" and "churned" are the same row — and T5's clawback branch now makes a money decision on it

- **Component:** `apps/api/src/routes/billing/billing-webhook.ts` (lines ~178-188, the `case 'subscription.cancelled': case 'subscription.completed':` fallthrough) · consumed by `apps/api/src/jobs/referral-qualify.ts` (T5)
- **Commit:** found 2026-09-22 while building T5. **Fixed 2026-09-24 in `72d3806d`** (owner ruling — see "Resolution" below). Everything from here to that bullet is kept **verbatim as the state at finding time**, including the "why deferred" reasoning and the reading of T5's decision; the ruling **revises** the latter.
- **Resolution (2026-09-24, owner):** the deferred owner decision came back **"a completed term is not churn."** The defect was fixed rather than re-documented, and the ruling overturns this entry's own "why the T5 decision is nevertheless CORRECT" argument — the argument was defensible on the spec's literal wording (*sustained paid **and** active*), but it priced a *successful, fully-paid* retailer as a churn and made the referrer's already-accrued commission the collateral. **The irreversibility is what decided it:** `CLAWED_BACK` has no undo (§11 / RC-036), so the strict reading buys nothing and costs an unrecoverable payout, while the lenient one leaves the accrual merely *uncollected* — a state a future rule can still address. Migration `116_subscription_status_completed` adds the enum value (its own migration, PG 55P04); the webhook now splits the two events onto **both** columns (`Subscription.status` and `Retailer.plan_status` — one enum, two columns, so fixing only one would have moved the collapse rather than removed it); `cancelled_at` is deliberately left null for a completion so the audit trail keeps the distinction the original bug destroyed; T5 keys on `CANCELLED` only, so a completed term falls through to the inert `NO_ACTIVE_SUBSCRIPTION` wait with nothing taken back; and the repeated `=== 'CANCELLED'` reads collapsed into a shared `isPlanEnded()` that treats both ended states alike while deliberately **excluding `PAST_DUE`** (dunning is recoverable — this entry's own T5 precedent). The "both events" test pair is the point: the webhook tests assert `COMPLETED` **and** that `cancelled` still writes `CANCELLED`, because a one-sided fix would have satisfied the bug report while relocating the collapse. **Reachability, stated honestly:** subscriptions are created with `total_count: 120`, so `subscription.completed` fires roughly a decade out — this is a correctness fix with a money reader, not a live-flow bug, and it should not be expected to fire before it is exercised by hand.
- **Symptom:** a retailer whose Razorpay subscription ran to its natural end (`subscription.completed`) is indistinguishable in the database from one who cancelled early. Both get `status: 'CANCELLED'`, `cancelled_at: <now>`, `Retailer.plan_status: 'CANCELLED'` and `razorpay_subscription_id: null`. Any consumer keying on `CANCELLED` — today, T5's churn clawback; tomorrow, churn analytics, win-back campaigns, or retention reporting — silently counts a successful completion as a loss.
- **Root cause:** **two distinct lifecycle events share one enum value because the enum has no room for the distinction.** `SubscriptionStatus` is `TRIAL | ACTIVE | PAST_DUE | CANCELLED` — there is no `COMPLETED`/`EXPIRED`, so the webhook had only two options (map a completion to `CANCELLED`, or invent a status) and chose the former. Every consumer downstream then inherits the ambiguity for free, because there is no column that preserves which event actually arrived. The collapse also overwrites the audit trail in the same statement: a completed subscription gets `cancelled_at` stamped and its `razorpay_subscription_id` nulled, so the original subscription cannot even be looked up afterwards to reconstruct what happened.
- **Why it was invisible:** nothing in the repo reads `CANCELLED` for a consequential decision until T5. The billing screens show a plan state, and "cancelled" reads as correct to a human either way — the information that distinguishes the two events is destroyed at write time, so no later query can recover it, and no test asserts the mapping's fidelity.
- **Why the T5 decision is nevertheless CORRECT (⚠️ revised 2026-09-24 — see "Resolution": the owner ruled completion is *not* churn; this argument is kept as the finding-time reading, not as current policy):** the qualify gate is *sustained paid **and** active through the window*, and a subscription that has completed is not active. Whether a retailer finished their term or left early, at the moment the conversion comes due they are not a paying, active customer — so `CLAWED_BACK` is the right outcome under the spec's rule. The defect is the **lost distinction**, not a wrong payout. Stated explicitly so this is not fixed "because the numbers are wrong" — they are not.
- **Why deferred:** the fix is a schema change (`COMPLETED` in the enum, or a `cancellation_reason` / `ended_reason` column) plus a webhook mapping change plus a backfill — i.e. it touches billing, which is the revenue path. Doing it silently from inside T5 would be a large, unrequested change to money-moving code under a task about referrals. RC-027's lesson applies in the opposite direction here: the engine string was fixed because it produced a **wrong image**; this one produces a **right decision from an ambiguous row**, so it is recorded and left for an owner decision.
- **Proof:** `apps/api/src/jobs/referral-qualify.test.ts` pins the consuming behaviour — "claws back a store that paid and then cancelled inside the window" asserts `CLAW_BACK / REFERRED_CHURNED_AFTER_PAYMENT`, and "qualifies when an ACTIVE subscription sits alongside an older cancellation" asserts that a mere historical cancellation does not claw back. Both are asserted by name so a future change to the mapping has to confront these tests rather than quietly alter a payout. **Added 2026-09-24 (the fix):** `apps/api/src/jobs/referral-qualify.test.ts` now also pins *"does NOT claw back a store whose paid term COMPLETED"* → `WAIT / NO_ACTIVE_SUBSCRIPTION` (falsified: adding `'COMPLETED'` to the `.some()` branch fails it) plus *"still claws back when a CANCELLED row sits alongside a later COMPLETED one"* — the 4.2 ruling's edge case, decided rather than inherited, **pinned by test so the reading is visible to whoever revisits it**. `apps/api/src/routes/billing.test.ts` gained the two webhook tests (a completion writes `COMPLETED` to both columns with no `cancelled_at`; a cancellation still writes `CANCELLED`), falsified by restoring the pre-fix mapping, which fails the completion arm — the webhook had **no test file at all** before this, which is why the original collapse survived review.
- **Prevention lesson:** **collapsing two states into one enum value destroys information at write time, and the loss only becomes visible at the first consumer that must act differently on the two.** When a webhook maps external event names onto an internal enum, the mapping is a *lossy* transformation and deserves the same suspicion as a unit conversion: ask what distinguishes the collapsed inputs and who will later need that distinction. Second-order rule this adds: **a job that makes a money decision from a status column should assert which source events can produce that status**, not merely that the status is handled — T5's tests do the latter, and this entry is the reminder that the former is still unverified.

- **Component:** `apps/api/src/routes/retailers/retailers-profile.ts` (`PUT /me`, the T4 capture call site) · `apps/api/src/lib/referral-conversions.ts` (the deliberate throw) · `packages/db/prisma/migrations/109_referral_program` (the dependency)

Nothing in the repo reports it: the route's own comment states the opposite, so a reviewer reads the promise rather than the behaviour.
- **Root cause:** **two independently-correct decisions that compose into a defect, because the only place the contradiction could be resolved had no code in it.**
  1. `applyReferralCapture()` **throws** on a database error, and its header says so deliberately: a capture that failed silently is a shop that was referred and a referrer who is never paid.
  2. The route was written non-fatal for referral problems, following the *same handler's* existing F-018 precedent ("silently ignored if invalid/blank"), and **documented that as a guarantee in a comment**. But the call site was a bare `await` — the comment asserted a contract that no `try`/`catch` implemented. A documented invariant with nothing enforcing it is a description of intent, not of behaviour.
  3. The trigger is a **deployment-order window the code cannot see**: migrations are applied by hand from the admin dashboard, while code deploys automatically from a push to `main`. Between those two events, `prisma.referralCode` typechecks (the schema declares the table) and every test with a mocked client passes, while the real database has no such table. No type, lint rule or test in this repo has an opinion on that gap.

And the failure only occurs on a non-empty code — an empty or absent field short-circuits before any query — so a smoke test that saves a profile without a code is green.
- **Fix:** the call site catches, logs the underlying error through `request.log.error`, and reports `referral: { status: 'CAPTURE_FAILED' }` as data. - **Prevention lesson:** **a library's deliberate throw and a caller's non-fatal contract are a contradiction that only the call site can resolve — and a comment asserting the contract is not the contract.** When the dependency of a captured value is a migration someone else applies by hand, the optional field must not be able to break the core flow, and the failure must still be reported: swallowing it converts a visible outage into an invisible lost referral, which is the worse of the two. Same shape as RC-027 and RC-029 — a fix (or a feature) whose real precondition is data or config that nothing verifies. Second-order rule this adds: **when a route comment claims a guarantee, the test file must be what asserts it.** Re-read every "never fails" / "always" comment in a file you are editing and check a `catch` is actually there.

## RC-031 — The affiliate/staff code separation rested on one character, and the guard protecting it checked only that a hyphen was *present* — so relaxing the pattern silently merged the two namespaces

- **Component:** `apps/api/src/lib/referral-codes.ts` (`isReservedForAffiliateNamespace`) · `apps/api/src/routes/team/team-members.ts` (the hand-editable F-018 field it guards)
- **Commit:** found 2026-09-22 by falsifying this feature's own new guard during T3; fixed the same session — `40e7d53b` (`feat(referrals): T3 affiliate code namespace + mint endpoint (RC-031)`)
- **Symptom:** nothing observable. The guard passed, the tests were green, and the failure it exists to prevent was reachable: a staff member typing `KAN7F3QMP` into the F-018 field would have it accepted, while `classifyReferralCode()` sent that same string to the **affiliate** ledger. One string, two ledgers, one of them paying the wrong actor.
- **Root cause:** the guard tested `value.includes('-')` — the presence of the separator — while the *requirement* is that the two namespaces be **disjoint**. Those are the same test only as long as the affiliate pattern keeps the hyphen mandatory. Relaxing it to `-?` (the kind of one-character change a later author makes to be "lenient about input") left `KAN7F3QMP` matching the affiliate pattern **and** the staff pattern, and the guard still passed because the string merely had to *contain* a hyphen somewhere. **The whole separation rested on one character, and nothing asserted that character was required.**
- **Why falsification found it and the test suite did not:** the existing tests all used well-formed codes, so they exercised the pattern in the one shape where presence and disjointness agree. Making the hyphen optional failed **nothing** — the guard was green for the wrong reason, which is the only way an invariant can be missing without any test noticing.
- **Fix:** the guard is now broader than the pattern it protects, in both directions — **any** hyphen is refused (a hand-typed `KAN-typo` is not a valid affiliate code either, but it is indistinguishable from the affiliate prefix to a human reading the column), **and** the hyphen-dropped shape is refused. - **Proof:** deliberately relaxing `AFFILIATE_CODE_PATTERN` to make the hyphen optional now fails the disjointness test with the offending code named. This was the **third** guard in the session that only held once it was deliberately broken.
- **Prevention lesson:** **when a guard's job is to keep two sets apart, assert the sets are disjoint — do not assert a proxy for it.** A test that the separator exists is not a test that the namespaces cannot overlap; the difference is invisible until the pattern changes, and by then the guard is the reason nobody looked. The generalisable habit: after writing any guard, break the thing it protects in the smallest plausible way and confirm the guard fails. If breaking it fails nothing, the guard is decorative.
