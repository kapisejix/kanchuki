## RC-039 — A test can outlive its own fixture: the fixture was one module-level object whose arrays `beforeEach` swapped, so a timed-out test wrote into the **next** test's state and the failure surfaced as a plausible wrong number in an unrelated assertion

- **Component:** `apps/api/src/routes/admin/admin-referral-monitor.test.ts` (prisma stand-in + `resetState`/`retireState`/`freshState`) · the same amplifier is present, unfired, in `apps/api/src/jobs/referral-payout.test.ts:220` (`resetState` reassigns `prismaState.*` on one shared object)
- **Commit:** found 2026-09-24 while chasing an intermittent `admin-referral-monitor` failure under the full parallel suite; fixed in the same session (test-infra only, no production code changed).
- **Symptom:** intermittent, roughly 1 full-suite run in 2–3, never in isolation and never in the same place twice:
  ```
  FAIL src/routes/admin/admin-referral-monitor.test.ts > GET /referral/overview > excludes FAILED batches from committed money
  AssertionError: expected 30000 to be +0
  ```
  The failing test seeds a single **FAILED** `20_000` payout and asserts `paid_out_paise === 0`. It read `30_000`, which is the *other* overview test's **PAID** row — so the failure reads as `GET /referral/overview` summing FAILED batches into committed money. It does not: the route was never wrong, and the number it was accused of was never in its input.
- **Root cause (two layers, and the first one is only a trigger):**
  1. **Trigger — a per-test dynamic import of the whole module graph.** This was the only file in 96 that built its app as `await Promise.all([import('fastify'), import('../../plugins/error-handler.js')])`, inside each test. Cheap alone; on a saturated worker the import exceeded vitest's 5s test timeout. Now static imports like every other suite.
  2. **Amplifier — the fixture was one object whose arrays were replaced.** `state` was a module-level `const` and `beforeEach(resetState)` did `state.payouts = []` (etc.). **Vitest abandoning a timed-out test does not cancel its promises.** `build()` resolved afterwards, the abandoned continuation ran its `seedConv`/`payouts.push` lines, and because `state` is a single object whose arrays had just been swapped, those writes landed in the **next test's freshly reset fixture**. Hence `30_000`.
  The two layers are independent: the leak is harmless without a timeout, and a timeout is harmless when each test owns its own fixture. Both are now addressed.
- **Why it survived review:** every locally visible reading is correct. The route's assertions are right; the failing test's seed is right; the mock is right; and the flake *looked* like a concurrency bug in the route, which is the kind of finding that gets "fixed" by loosening the assertion. Nothing in the file names the real invariant (a test's fixture must not be readable by the next test), and no assertion could see it — a leaked row is not distinguishable from a seeded one at read time.
- **Fix (two halves — and the first half, shipped alone, changed nothing):**
  - **Ownership (the actual fix):** the fixture became `let state: Fixture` swapped whole — `resetState()` is now `state = makeState()`, and a test's first statement is `const st = freshState()`. A late write then goes into the abandoned test's **own, now-unreferenced** object, which the next test cannot see at any timing.
  - **Retiring (the amplifier's alarm):** `afterEach(retireState)` freezes the retired fixture's arrays, so a late write **throws** (`Cannot add property 5, object is not extensible`) inside the abandoned promise chain instead of landing silently. Frozen *without* ownership this does nothing — it freezes arrays the next `beforeEach` immediately replaces, which is exactly why the freeze shipped first, was tested, and **did not stop the flake**.
  - **Guards (F6–F8):** F6 replays the mechanism deterministically (`abandoned`/`next` fixtures must be different objects, and the late write must throw); F8a/F8b pin the **wiring** F6 cannot see; F7 is a source scan asserting no test body writes the shared pointer.
- **Two guard defects found while proving it — both were green in their own mutant, which is the only reason they were caught:**
  1. **A guard that located itself by a literal filename.** F7 read `join(HERE, 'admin-referral-monitor.test.ts')`, so injecting a bare `state.payouts.push(…)` into a *copy* of the file left it green — it had scanned the original. Now `fileURLToPath(import.meta.url)`, i.e. always this file. Any guard that names its own path is one rename away from silently scanning something else.
  2. **A guard that pinned a function without its wiring.** F6 calls `retireState()` itself, so **deleting `afterEach(retireState)` left the suite at 32/32 green**. Measured, not assumed: the F6 comment first claimed the deletion would turn it red, and the experiment disproved the comment. F6 keeps the function half; F8b (a later test reading a fixture captured by an earlier one) covers the registration.
- **Proof:** `admin-referral-monitor.test.ts` **34/34** (was 32; +F8a/F8b, +F7 rewritten). Falsified three ways, each red for its own reason: **(A)** `resetState` back to clearing arrays on one shared object → F6 + F8b red (`expected [] not to be []` — the message itself shows one array); **(B)** `afterEach(retireState)` deleted → F8b red only (`expected false to be true`), F6 correctly stays green; **(C)** a bare `state.payouts.push(…)` in a test body → F7 red, naming the call. Full API suite **1353 passed / 5 skipped (1358), 0 failed, twice consecutively** under the default parallel run — the first clean back-to-back runs this file has had. `tsc` + biome clean.
- **Prevention lesson:** **a test fixture has a lifetime, and nothing in vitest enforces it** — an abandoned test is not a cancelled one, so any per-test state reachable by identity can be written by the test that just gave up. The check is mechanical: per-test state must be *owned* (created per test, reached only through a per-test binding), never *shared and cleared*. The second lesson is about the guards themselves: **a guard is only as good as its mutant** — a source scan that resolves its own path from a string, or a mechanism test that supplies its own precondition, will report green while the wiring it exists to protect is gone. Both failures here were found by running the mutation, not by reading the code.

## RC-038 — `SubscriptionPayment.status` advertised `refunded` in its own column comment and nothing in the repo could write it, so three consumers asked "was this month paid for?" — and one of them documented the impossible behaviour as a feature

- **Component:** `packages/db/prisma/schema.prisma:1010` (`status String // success | failed | refunded`) · `apps/api/src/routes/billing/billing-webhook.ts` (no `refund.*` case existed) · its three consumers: `jobs/referral-accrue.ts` (T6), `jobs/referral-qualify.ts` (T5), `routes/admin/admin-commission.ts` (§42)
- **Commit:** found 2026-09-24 while working the post-referral cleanup board (§5A.1); **fixed the same session in `13b50ea8`** (the entry was written by the fix rather than after it — the board had carried "nothing writes `refunded`" as an open item since 2026-09-22).
- **Symptom:** *none observable* — which is the whole finding. Every downstream behaviour was correct **for the only input that could exist**: the month was always `success`, so T6 always accrued, T5 always saw a successful payment, and the §42 pool always summed the same rows. A missing writer produces no error, no log line and no red test; it produces a *narrower* system that behaves correctly.
- **Root cause:** **a status value with a documented meaning and no producer.** The column comment listed `success | failed | refunded` as though all three were states the system could reach, and only `success` was ever written. Two consequences follow, and they pull in opposite directions:
  1. All three consumers encoded `status: 'success'` — a correct **whitelist**, and one that reads as defensive rather than as evidence that the other branches cannot happen. Nothing distinguishes "we designed for the success case" from "we never built the rest".
  2. `admin-commission.ts`'s file header asserted the *opposite*: "a refunded/voided payment immediately reduces the month's pool". That sentence is not wrong, it is **unfalsifiable** — the pool is computed from `status: 'success'` rows, so it genuinely would shrink, on an event no code in the repository could produce. A claim whose trigger does not exist reads as coverage to every future reviewer.
  Same shape as RC-025 (the proxy route that never existed) and RC-027's phantom parameters: **the contract was described in one file and implemented in none**, and description is what a reader trusts.
- **Why it survived review:** each piece is individually defensible, and the gap is only visible by asking where a value is *written*. Reading the consumers shows careful, whitelist-based code; reading the schema shows a status enum that mentions refunds; reading §42 shows a refund behaviour that "already works". All three readings are locally correct, and no test can fail on an event nothing emits. The referral work is what surfaced it: T5/T6 are the first consumers to make a *money* decision from that column, so the missing half finally had a reason to exist.
- **Fix (§5A.1):** `refund.processed` → `SubscriptionPayment.status = 'refunded'`, idempotent via the WHERE (`status: { not: 'refunded' }`), unknown payment row → warn + 200. **Placed above the subscription lookup**, which is the load-bearing part: the existing `if (!rzpSub) return reply.send({ received: true })` would have dropped every refund — a refund event need not carry `payload.subscription` — silently, as an HTTP **200**. Only `refund.processed`; `created`/`failed` do not mean money moved back. Partial refunds are logged and not applied (owner decision 2026-09-24: a plan charge is refunded in full or not at all; a partial would need a `refunded_amount` column, migration 117, and a pro-rata rule).
- **Proof:** the placement test asserts the **write happened**, not the status code — the broken version also answers 200, so a response-code test would have been green in the bug's world. `billing.test.ts` +6 (30/30): applies to the matching row on a payload with **no** subscription entity; a replay is a 0-row no-op; a partial is not applied; an unknown row writes nothing and still 200s; a bad signature is still 401 for this event. **Falsified:** reinstating the `if (!payload.subscription?.entity) return { received: true }` guard fails the three refund tests (the 401 arm stays green, correctly — signature precedes everything). T6 gained 3 tests (32/32) — a refunded month does not earn and does not consume an installment, **a month already earned is never un-earned**, and the loader filter is an exact whitelist (asserted as a form, so relaxing it to `not: 'refunded'` fails). T5 gained 2 (28/28). Full API 1349/1354 (5 skips), tsc + biome clean.
- **Prevention lesson:** **when a column comment or file header enumerates values a system can reach, the enumeration is a claim about writers, and nothing tests it.** A consumer's whitelist is not evidence that the other cases are impossible — it is evidence that only one case was ever observed. The check is cheap and belongs in review: for every literal in a status/enum comment, grep for a write of it; a value with readers and no writer is either dead documentation or an unbuilt feature, and the two are indistinguishable from the read side. Second-order rule this adds: **a comment that describes behaviour triggered by an event no code emits must say so** — "a refunded payment reduces the pool" and "a refunded payment would reduce the pool, but nothing writes `refunded`" are the same sentence to a maintainer and opposite statements to an operator. Same family as RC-025/RC-031: the guard or contract exists as *text*, in a place no test reads.

## RC-037 — Mocks that return the same object they store made three payout bugs invisible: an in-memory-only resize, a plugin-scoped raw-body hook, and a Prisma enum the DB never had

- **Component:** F-038 T7 — `jobs/referral-payout.ts`, `routes/webhooks/razorpayx-payout.ts`, `lib/referral-payout-account-save.ts`, migration 113 · found by the 2026-09-23 full-feature review
- **Commit:** this session
- **Root causes (one shape — the test double agreed with the code, not with the platform):**
  1. **RC-036's partial-claim resize never reached the DB.** It mutated the JS object `tx.referralPayout.create()` returned; `submitPayoutRow` re-reads the row, so RazorpayX would have been paid the stale figure. The mock's `create` pushed and returned the *same* object, so the mutation leaked into "the DB" and the test passed.
  2. **Every RazorpayX webhook would 401.** `request.rawBody` is set by a `preParsing` hook registered inside `billingRoutes`; Fastify hooks are plugin-scoped, and the payout webhook is a separate plugin, so `rawBody` was always undefined. Source-scan tests checked the secret name, never that the body was captured.
  3. **Every payout-account save would fail.** `schema.prisma` declares enum `referral_payout_account_type` (BANK_ACCOUNT/VPA); migration 113 made the column TEXT with a lowercase CHECK and never created the type. Mocked Prisma never casts. 113 also stored raw bank/UPI details the owner decision said must never persist — and nothing read them.
- **Also fixed (logic, same review):** (4) the claim attached only `payout_id IS NULL` conversions, but a PAID batch keeps its conversions attached while they keep accruing, so after a referrer's **first** payout nothing ever re-attached — every later month hit `EmptyClaimError` and was never paid. (5) Any submit exception (timeout, 5xx) released the claim; the money was then re-batched under a **new** idempotency key — a double-pay whenever RazorpayX had in fact created the payout.
- **Fix:** claim tx takes `pg_advisory_xact_lock(hashtext(referrer_id))`, re-reads the ledger under it, creates the batch at that amount (no post-hoc resize), and attaches conversions that are unattached **or** held by a PAID batch. `RazorpayxHttpError.isDefinitiveRejection` (4xx except 408/429) is the only thing that releases a claim; anything else leaves the row PENDING for same-key re-submit. Shared `captureRawBody` hook (billing, WhatsApp, RazorpayX — three copies → one) added to the payout webhook. Migration `115_referral_payout_account_fix` (**owner must apply**) converts the column to the enum and drops `bank_details`/`vpa_address`.
- **Proof:** payout job 53/53 incl. new tests (ambiguous 5xx stays PENDING and re-submits with the same key; second payout after a PAID batch; race loser/partial via a hooked lock). Falsified: forcing every error "definitive" → ambiguous test red; sizing from the pre-read → partial-race + F1 red. Full API 1327/1332 (5 skips), tsc clean.

## RC-036 — The payout job read the money BEFORE the claim transaction, and sized the batch from that stale figure: the CAS prevented a double-**attach** but nothing prevented a double-**pay**

- **Component:** `apps/api/src/jobs/referral-payout.ts` (`handleReferralPayout` claim tx) · found by the §11 checklist run (RC-015 row, server half)
- **Commit:** this session
- **Root cause:** the per-run unsettled amount is read **outside** the claim transaction (`Promise.all` of account + conversions + ledger aggregate), and `decideReferrerBatch` sizes the batch from that pre-read figure. Under overlap — manual trigger + cron, or two manual triggers (the web button's guard is React state, and RC-015 exists precisely because state-only guards don't survive concurrent entry) — both runs read `unsettled = ₹1000` and both enter the claim tx. The CAS (`payout_id IS NULL`) correctly makes one run attach zero conversions… but the run then created the PENDING batch **before** the CAS, with `amount_paise = 10000` (the stale figure), and `submitPayoutRow` pays whatever the batch says. `settlePayout('PAID')` would have moved real money with no ledger conversion behind it — invisible until reconciliation, because every row's own CHECKs hold (a batch with no conversions is not a constraint violation).
- **Why it was invisible:** every single-threaded test passes — the CAS looks like it covers the race, and in the single-run case the pre-read figure is always correct. The gap exists only in the ordering between two concurrent runs, which no test in the repo simulated.
- **The shape of the fix (two guards, one per way the race loses money):** inside the claim tx, (1) re-sum what **this batch actually attached** (`tx.referralConversion.aggregate` by `payout_id`); if the CAS attached zero → `EmptyClaimError`, unwinding the tx so the loser's batch row is discarded exactly as Postgres would roll it back, surfaced as a new `skipped_concurrent` counter (not an error — the winner's batch is authoritative). (2) If the claim is **partial** (`claimedGross < grossPaise`), resize the batch (`amount_paise`/`tds_paise` via `splitTds` re-applied) to what it actually holds before the audit row — the audit metadata and the submitted amount both derive from `batch.amount_paise`, so the ledger and the payment can never disagree.
- **Proof:** 51/51 job tests, two new mechanism tests — empty claim → `skipped_concurrent=1`, no `createPayout` call, zero surviving batch rows; partial claim → RazorpayX receives 15000 (the tx's own re-sum), never the stale 60000. Falsified both ways: removing the throw → race test red (`skipped_concurrent` 0 ≠ 1, the loser proceeded); disabling the resize → race test red (`amount: 60000` submitted). The test harness's mock `$transaction` gained real rollback semantics (snapshot mutable state, restore on throw) — without it the loser's batch row survived the tx throw and the test asserted the mock's limitation rather than the DB's behavior. Full API suite 1325/1330 (5 skips), tsc + Biome clean.

## RC-034 — The rule "which admin surfaces need Super Admin" lived in three hand-written lists that had drifted apart, and the only copy that enforced anything failed **open** — so a plain ADMIN key could reach surfaces the UI hides

- **Component:** `apps/api/src/routes/admin-auth.ts` (`adminAuthPreHandler`) · `apps/web/src/app/admin/layout.tsx` · `apps/web/src/app/admin/components/Sidebar.tsx` · new `packages/shared/src/constants/admin-access.ts` + `apps/api/src/routes/admin-access.test.ts`
- **Commit:** this session
- **Symptom:** a plain (non-`SUPER_ADMIN`) admin key could read **and write** `commission` (the 3% payout ledger), `referral-settings` (referral payout terms), `addon-purchases`, `ai-usage`, `audit-log`, `plan-features`, `plan-limits`, `resource-packs` and `storage-report` — every one of which the web UI hides from that role. On top of those, `plan-pricing` (what every retailer is charged), `invoices` (tax documents) and `database/deletion-vault` (hard-deletes retailer/customer data) were in **no** list at all.
- **Root cause:** **three copies of one rule — measured 8 / 14 / 14 entries — with the enforcement sitting in the copy that failed open.** Each surface was protected in whichever list somebody happened to edit, and the API's check was `path.startsWith(...)` against a fixed set, so a route nobody remembered to add was *reachable* rather than *refused*. The failure mode is silent by construction: no error, no log, the surface is simply open. Adding an admin route was therefore a security decision that defaulted to "public".
- **Why it was invisible:** the web UI *looked* correct — the Sidebar hid the entries and the layout rendered "Access Restricted" — so the panel appeared to enforce the rule. Only the API did, and only for the eight segments in its list. `referral-settings` existed in the Sidebar alone, and the three segments in no list were invisible from any single file.
- **The shape of the fix:** one shared list consumed by all three surfaces, **and** a guard that derives the segment set from the route sources, so "which segments exist" is measured rather than remembered. Because the runtime check fails open by design, the completeness property can only live in a test that re-reads the repo. Everything is classified **including the permitted**: with both lists present the question becomes "which of these two is it?" rather than the lazily-answerable "is this sensitive?", and the failure message names the segment *and* the file that declares it.
- **Also fixed as a by-product:** `payments` was in the API list while matching no route, so it protected nothing; and five more entries (`theme`, `catalog-promo`, `rate-limits`, `notifications`, `ticket-reporting`) turned out to be dead for a reason worth recording — those files are named after the *feature*, but the **first path segment** is the parent prefix (`/settings/theme`, `/reporting/tickets`), so a list keyed on filenames protects nothing. The guard's dead-entry assertion is what stops this recurring.
- **Proof:** `admin-access.test.ts` 11/11, falsified three ways — removing a gated entry (`referral-settings`) failed and named the path; adding a new admin route file failed and named that file; reintroducing the old `startsWith` semantics failed the sibling-segment assertion (`/admin/commission-x` must **not** match `commission`). API 1215/1215, web 321/321.
- **Flagged in this change, then decided 2026-09-24:** `team-members` (staff account management — credential-adjacent) and `reports` (`/admin/reports/gst` *is* tax data) shipped as standard-admin, matching their pre-change reachability, each with an in-file note carrying the one-line change. **Both were moved into `SUPER_ADMIN_ONLY_ADMIN_SEGMENTS` on 2026-09-24** (board §3), the notes deleted — and the decision was **pinned rather than documented**: `admin-access.test.ts` now asserts all four paths (`/admin/team-members`, `/admin/team-members/anything`, `/admin/reports`, `/admin/reports/gst`, plus `/v1/admin/reports`) and `Sidebar.test.tsx` asserts the nav for **both** roles. Both were falsified by moving the segments back. Side effect checked and asserted: every child of the *Reports & Finance* group is now super-admin-only (`reports` was its last standard-admin entry), so the group disappears for a plain ADMIN.
- **Residual — deliberately NOT fixed on 2026-09-24:** both pages fetch their *data* from `/v1/team/*`, which no list here covers. `teamAuthPreHandler` accepts any valid admin key and grants it unscoped Super Admin, so a plain-ADMIN caller still reaches `/v1/team/members` (including `POST` with `role: 'SUPER_ADMIN'`) and `/v1/team/reporting/*`. **The pages are closed; the routes behind them are not.** Kept separate because the `ADMIN` role is currently latent (`signAdminSession` always signs `SUPER_ADMIN`, and `TeamRole` has no `ADMIN`) and blanket-gating `/v1/team/*` would remove a shipped capability (managers creating their own agents). Recorded as a scope note in `admin-access.ts` and on the board (§3.3).

## RC-035 — A test assertion pinned to one mutable data row went stale, and a **gitignored build artifact** hid it: the suite was passing against an old `dist`, not against the source

- **Component:** `apps/web/src/lib/__tests__/studio-bench.test.ts` ("returns null — never a guess — when the price is unverified") · `packages/shared/src/constants/index.ts` (`STUDIO_ENGINE_INFO`)
- **Commit:** pre-existing at HEAD, surfaced and fixed this session (see the admin-access commit)
- **Symptom:** `studioEngineCost('grok_imagine')` was asserted to be `null`, but the committed table says `usd: 0.04`, so a fresh `pnpm build` turned the web suite red. With the stale artifact present, it was green.

## RC-033 — The billing webhook collapses `subscription.completed` into `Subscription.status = CANCELLED`, so "finished its paid term" and "churned" are the same row — and T5's clawback branch now makes a money decision on it

- **Component:** `apps/api/src/routes/billing/billing-webhook.ts` (lines ~178-188, the `case 'subscription.cancelled': case 'subscription.completed':` fallthrough) · consumed by `apps/api/src/jobs/referral-qualify.ts` (T5)
- **Commit:** found 2026-09-22 while building T5. **Fixed 2026-09-24 in `72d3806d`** (owner ruling — see "Resolution" below). Everything from here to that bullet is kept **verbatim as the state at finding time**, including the "why deferred" reasoning and the reading of T5's decision; the ruling **revises** the latter.
- **Resolution (2026-09-24, owner):** the deferred owner decision came back **"a completed term is not churn."** The defect was fixed rather than re-documented, and the ruling overturns this entry's own "why the T5 decision is nevertheless CORRECT" argument — the argument was defensible on the spec's literal wording (*sustained paid **and** active*), but it priced a *successful, fully-paid* retailer as a churn and made the referrer's already-accrued commission the collateral. **The irreversibility is what decided it:** `CLAWED_BACK` has no undo (§11 / RC-036), so the strict reading buys nothing and costs an unrecoverable payout, while the lenient one leaves the accrual merely *uncollected* — a state a future rule can still address. Migration `116_subscription_status_completed` adds the enum value (its own migration, PG 55P04); the webhook now splits the two events onto **both** columns (`Subscription.status` and `Retailer.plan_status` — one enum, two columns, so fixing only one would have moved the collapse rather than removed it); `cancelled_at` is deliberately left null for a completion so the audit trail keeps the distinction the original bug destroyed; T5 keys on `CANCELLED` only, so a completed term falls through to the inert `NO_ACTIVE_SUBSCRIPTION` wait with nothing taken back; and the repeated `=== 'CANCELLED'` reads collapsed into a shared `isPlanEnded()` that treats both ended states alike while deliberately **excluding `PAST_DUE`** (dunning is recoverable — this entry's own T5 precedent). The "both events" test pair is the point: the webhook tests assert `COMPLETED` **and** that `cancelled` still writes `CANCELLED`, because a one-sided fix would have satisfied the bug report while relocating the collapse. **Reachability, stated honestly:** subscriptions are created with `total_count: 120`, so `subscription.completed` fires roughly a decade out — this is a correctness fix with a money reader, not a live-flow bug, and it should not be expected to fire before it is exercised by hand.
- **Symptom:** a retailer whose Razorpay subscription ran to its natural end (`subscription.completed`) is indistinguishable in the database from one who cancelled early. Both get `status: 'CANCELLED'`, `cancelled_at: <now>`, `Retailer.plan_status: 'CANCELLED'` and `razorpay_subscription_id: null`. Any consumer keying on `CANCELLED` — today, T5's churn clawback; tomorrow, churn analytics, win-back campaigns, or retention reporting — silently counts a successful completion as a loss.
- **Root cause:** **two distinct lifecycle events share one enum value because the enum has no room for the distinction.** `SubscriptionStatus` is `TRIAL | ACTIVE | PAST_DUE | CANCELLED` — there is no `COMPLETED`/`EXPIRED`, so the webhook had only two options (map a completion to `CANCELLED`, or invent a status) and chose the former. Every consumer downstream then inherits the ambiguity for free, because there is no column that preserves which event actually arrived. The collapse also overwrites the audit trail in the same statement: a completed subscription gets `cancelled_at` stamped and its `razorpay_subscription_id` nulled, so the original subscription cannot even be looked up afterwards to reconstruct what happened.
- **Why it was invisible:** nothing in the repo reads `CANCELLED` for a consequential decision until T5. The billing screens show a plan state, and "cancelled" reads as correct to a human either way — the information that distinguishes the two events is destroyed at write time, so no later query can recover it, and no test asserts the mapping's fidelity.
- **Why the T5 decision is nevertheless CORRECT (⚠️ revised 2026-09-24 — see "Resolution": the owner ruled completion is *not* churn; this argument is kept as the finding-time reading, not as current policy):** the qualify gate is *sustained paid **and** active through the window*, and a subscription that has completed is not active. Whether a retailer finished their term or left early, at the moment the conversion comes due they are not a paying, active customer — so `CLAWED_BACK` is the right outcome under the spec's rule. The defect is the **lost distinction**, not a wrong payout. Stated explicitly so this is not fixed "because the numbers are wrong" — they are not.
- **Why deferred:** the fix is a schema change (`COMPLETED` in the enum, or a `cancellation_reason` / `ended_reason` column) plus a webhook mapping change plus a backfill — i.e. it touches billing, which is the revenue path. Doing it silently from inside T5 would be a large, unrequested change to money-moving code under a task about referrals. RC-027's lesson applies in the opposite direction here: the engine string was fixed because it produced a **wrong image**; this one produces a **right decision from an ambiguous row**, so it is recorded and left for an owner decision.
- **Proof:** `apps/api/src/jobs/referral-qualify.test.ts` pins the consuming behaviour — "claws back a store that paid and then cancelled inside the window" asserts `CLAW_BACK / REFERRED_CHURNED_AFTER_PAYMENT`, and "qualifies when an ACTIVE subscription sits alongside an older cancellation" asserts that a mere historical cancellation does not claw back. Both are asserted by name so a future change to the mapping has to confront these tests rather than quietly alter a payout. **Added 2026-09-24 (the fix):** `apps/api/src/jobs/referral-qualify.test.ts` now also pins *"does NOT claw back a store whose paid term COMPLETED"* → `WAIT / NO_ACTIVE_SUBSCRIPTION` (falsified: adding `'COMPLETED'` to the `.some()` branch fails it) plus *"still claws back when a CANCELLED row sits alongside a later COMPLETED one"* — the 4.2 ruling's edge case, decided rather than inherited, **pinned by test so the reading is visible to whoever revisits it**. `apps/api/src/routes/billing.test.ts` gained the two webhook tests (a completion writes `COMPLETED` to both columns with no `cancelled_at`; a cancellation still writes `CANCELLED`), falsified by restoring the pre-fix mapping, which fails the completion arm — the webhook had **no test file at all** before this, which is why the original collapse survived review.
- **Prevention lesson:** **collapsing two states into one enum value destroys information at write time, and the loss only becomes visible at the first consumer that must act differently on the two.** When a webhook maps external event names onto an internal enum, the mapping is a *lossy* transformation and deserves the same suspicion as a unit conversion: ask what distinguishes the collapsed inputs and who will later need that distinction. Second-order rule this adds: **a job that makes a money decision from a status column should assert which source events can produce that status**, not merely that the status is handled — T5's tests do the latter, and this entry is the reminder that the former is still unverified.

## RC-032 — A library that throws on purpose was wired into a route whose own comment promised it could not fail, with no catch at the boundary — so an unapplied migration would 500 the onboarding save

- **Component:** `apps/api/src/routes/retailers/retailers-profile.ts` (`PUT /me`, the T4 capture call site) · `apps/api/src/lib/referral-conversions.ts` (the deliberate throw) · `packages/db/prisma/migrations/109_referral_program` (the dependency)
- **Commit:** found 2026-09-22 while building T4; fixed before the task's commit — the code is in `apps/api/src/routes/retailers/retailers-profile.ts` with the guard in `apps/api/src/routes/retailers/retailers-profile.test.ts`
- **Symptom (had it shipped):** `PUT /v1/retailers/me` returns **500** for any retailer whose payload contains a non-empty `referral_code`, for as long as migrations 109/110/111 are unapplied — i.e. **onboarding is blocked** for exactly the users who tried to enter a referral code, which is the behaviour the affiliate program exists to encourage. Nothing in the repo reports it: the route's own comment states the opposite, so a reviewer reads the promise rather than the behaviour.
- **Root cause:** **two independently-correct decisions that compose into a defect, because the only place the contradiction could be resolved had no code in it.**
  1. `applyReferralCapture()` **throws** on a database error, and its header says so deliberately: a capture that failed silently is a shop that was referred and a referrer who is never paid.
  2. The route was written non-fatal for referral problems, following the *same handler's* existing F-018 precedent ("silently ignored if invalid/blank"), and **documented that as a guarantee in a comment**. But the call site was a bare `await` — the comment asserted a contract that no `try`/`catch` implemented. A documented invariant with nothing enforcing it is a description of intent, not of behaviour.
  3. The trigger is a **deployment-order window the code cannot see**: migrations are applied by hand from the admin dashboard, while code deploys automatically from a push to `main`. Between those two events, `prisma.referralCode` typechecks (the schema declares the table) and every test with a mocked client passes, while the real database has no such table. No type, lint rule or test in this repo has an opinion on that gap.
- **Why it was invisible:** the 500 lands on the *profile save*, so it presents as a profile-validation bug rather than as a missing table. And the failure only occurs on a non-empty code — an empty or absent field short-circuits before any query — so a smoke test that saves a profile without a code is green.
- **Fix:** the call site catches, logs the underlying error through `request.log.error`, and reports `referral: { status: 'CAPTURE_FAILED' }` as data. Both halves of the requirement hold at once: the save cannot fail, and the failure is not swallowed. `ReferralCaptureReport` was added as the caller-facing type precisely so the next consumer (T5's qualify gate) sees that the caller's outcome set is one member wider than the library's return set, instead of re-deriving it.
- **Proof:** `apps/api/src/routes/retailers/retailers-profile.test.ts` — with the lookup rejecting, the response is **200**, the row is actually written (`retailer.update` called once), and `referral` is `{ status: 'CAPTURE_FAILED' }`; a second test asserts the log carries the underlying error's **message**, because "non-fatal" must not mean "invisible". **Falsified:** restoring `throw error` inside the catch fails both with `expected 500 to be 200`.
- **Prevention lesson:** **a library's deliberate throw and a caller's non-fatal contract are a contradiction that only the call site can resolve — and a comment asserting the contract is not the contract.** When the dependency of a captured value is a migration someone else applies by hand, the optional field must not be able to break the core flow, and the failure must still be reported: swallowing it converts a visible outage into an invisible lost referral, which is the worse of the two. Same shape as RC-027 and RC-029 — a fix (or a feature) whose real precondition is data or config that nothing verifies. Second-order rule this adds: **when a route comment claims a guarantee, the test file must be what asserts it.** Re-read every "never fails" / "always" comment in a file you are editing and check a `catch` is actually there.

## RC-031 — The affiliate/staff code separation rested on one character, and the guard protecting it checked only that a hyphen was *present* — so relaxing the pattern silently merged the two namespaces

- **Component:** `apps/api/src/lib/referral-codes.ts` (`isReservedForAffiliateNamespace`) · `apps/api/src/routes/team/team-members.ts` (the hand-editable F-018 field it guards)
- **Commit:** found 2026-09-22 by falsifying this feature's own new guard during T3; fixed the same session — `40e7d53b` (`feat(referrals): T3 affiliate code namespace + mint endpoint (RC-031)`)
- **Symptom:** nothing observable. The guard passed, the tests were green, and the failure it exists to prevent was reachable: a staff member typing `KAN7F3QMP` into the F-018 field would have it accepted, while `classifyReferralCode()` sent that same string to the **affiliate** ledger. One string, two ledgers, one of them paying the wrong actor.
- **Root cause:** the guard tested `value.includes('-')` — the presence of the separator — while the *requirement* is that the two namespaces be **disjoint**. Those are the same test only as long as the affiliate pattern keeps the hyphen mandatory. Relaxing it to `-?` (the kind of one-character change a later author makes to be "lenient about input") left `KAN7F3QMP` matching the affiliate pattern **and** the staff pattern, and the guard still passed because the string merely had to *contain* a hyphen somewhere. **The whole separation rested on one character, and nothing asserted that character was required.**
- **Why falsification found it and the test suite did not:** the existing tests all used well-formed codes, so they exercised the pattern in the one shape where presence and disjointness agree. Making the hyphen optional failed **nothing** — the guard was green for the wrong reason, which is the only way an invariant can be missing without any test noticing.
- **Fix:** the guard is now broader than the pattern it protects, in both directions — **any** hyphen is refused (a hand-typed `KAN-typo` is not a valid affiliate code either, but it is indistinguishable from the affiliate prefix to a human reading the column), **and** the hyphen-dropped shape is refused. A test asserts a hyphen-stripped minted code classifies **neither** `AFFILIATE` nor `STAFF`, so a future relaxation of the pattern fails the suite instead of the ledger. `KAN001` still classifies `STAFF` (the affiliate alphabet omits `0`/`1`/`I`/`L`/`O`), which is why reserving the `KAN` prefix outright was rejected — it would have broken the existing F-018 fixture for no gain.
- **Proof:** deliberately relaxing `AFFILIATE_CODE_PATTERN` to make the hyphen optional now fails the disjointness test with the offending code named. This was the **third** guard in the session that only held once it was deliberately broken.
- **Prevention lesson:** **when a guard's job is to keep two sets apart, assert the sets are disjoint — do not assert a proxy for it.** A test that the separator exists is not a test that the namespaces cannot overlap; the difference is invisible until the pattern changes, and by then the guard is the reason nobody looked. The generalisable habit: after writing any guard, break the thing it protects in the smallest plausible way and confirm the guard fails. If breaking it fails nothing, the guard is decorative.

## RC-030 — A denormalised `retailer_id` (bare scalar, no FK) gives the purge path no way to know a table exists, so new features silently strand rows on retailer deletion

- **Component:** `packages/db/prisma/schema.prisma` (7 models) · `apps/api/src/jobs/purge-soft-deleted.ts` (cron) · `apps/api/src/jobs/purge-retailer-now.ts` (admin hard-delete) · `scripts/setup-role-separation.sql` · `packages/db/prisma/migrations/110_promotions_purge_grant` · `packages/db/prisma/migrations/111_backend_role_rls_policies` (the RLS half) · `apps/api/src/jobs/purge-rls-policy.test.ts` + `purge-rls-live.test.ts`
- **Commit:** found 2026-09-22 while auditing `scripts/setup-role-separation.sql` against the schema (RC-029); fixed the same session — all 7 sweeps added to both purge jobs, the 5 missing grants added, and the completeness gap closed by test
- **Symptom:** nothing errors. Deleting a retailer (15-day cron or the admin hard-delete) leaves that retailer's rows behind in seven tables, permanently: `campaigns`, `campaign_sends`, `promotions`, `consent_events`, `customer_recently_viewed`, `customer_wishlist_items`, `customer_interactions`. Two of the seven are not even granted to the purge role, so the delete could not succeed if it were attempted.
- **Root cause:** **the purge path is a hand-maintained list, and nothing connects it to the schema.** A table gets `retailer_id` as a bare `String` — no `@relation`, deliberately, to avoid the RESTRICT-FK child problem — which means Postgres will neither cascade the delete nor raise an FK violation when it is missed. The two failure modes of a *declared* FK are loud (13503 blocks the delete; CASCADE does the work); the failure mode of a denormalised column is silent, and the row simply survives. Nothing about adding a column called `retailer_id` forces an author to learn the list exists, and no test asserts the list is complete — only that its existing entries are present. 6 of the 13 models with a bare `retailer_id` are purged; 7 are not.
- **Why it is worse than untidy:** the stranded rows are another party's personal data — a deleted retailer's customer interaction logs, wishlists and consent records are retained indefinitely with no owner. Under DPDP that is a retention and deletion failure, not just hygiene. `docs/SECURITY.md` §19 sets the deletion expectation the job is supposed to meet.
- **Fix:** all 7 now get the child sweep in **both** jobs (`purgeChildren(…)` in the cron, `DELETE FROM … WHERE retailer_id = $1` in the hard-delete) plus a `GRANT DELETE` — 6 in `scripts/setup-role-separation.sql`, `promotions` in migration `110`. `product_videos` proved the pattern works; the gap was that it was never generalised. The four `customer_*`/`consent_*` tables then turned out to be only half a fix — see the RLS bullet below, which was found by asking whether the sweeps would actually delete anything.
- **Second half of the same symptom, from an unrelated direction (RLS):** with the sweeps and grants in place the four `customer_*`/`consent_*` tables *still* deleted nothing. They have ROW LEVEL SECURITY enabled (migrations 079/100 — no policy means default deny) and `kanchuki_purge` is created **without `BYPASSRLS`**, while RLS *filters* rows rather than raising: the statement commits, 0 rows change, and nothing logs. The tempting reading was "those four are special", and it was wrong — **23 of the 32** tables this path deletes from are RLS-enabled (`products`, `customers`, `collections`, `retailers`, `subscriptions`, `staff`, `audit_logs`…), and **not one policy in the entire schema named `kanchuki_app` or `kanchuki_purge`** — every policy targets `authenticated`/`anon`, the PostgREST roles. The whole path worked only via `pg_class_ownercheck`: `kanchuki_purge` is a member of `kanchuki_app`, so for any table `kanchuki_app` *owns*, both are treated as owners and skip RLS. That is an accident of which role ran which migration (base schema via Prisma, 083–089 via the admin runner on `DATABASE_URL_MIGRATOR`, others from dev machines on the `kanchuki_app`-scoped `.env`), it is per-table, and nothing verified or recorded it. So the honest diagnosis was not "four tables lack a policy" but "the backend's access to all 50 RLS tables rests on an undocumented ownership accident, and RC-030 is where it first bit."
- **Fix (RLS half):** migration `111_backend_role_rls_policies` creates one `FOR ALL … USING (true) WITH CHECK (true)` policy per RLS table the purge path touches, naming both backend roles — 24 tables, derived from the job sources rather than typed by hand. A policy and not `ALTER ROLE … BYPASSRLS` (needs superuser, so it could only ever be hand-applied in the SQL Editor — the RC-029 failure exactly; and it would silently cover future tables with no trace in the schema). **`FOR ALL` rather than `FOR DELETE` is the trap:** `purgeTable()` selects a batch of ids and exits when the batch is empty, `fetchR2Keys()` selects keys before the rows go, and `purgeChildren()` scopes its `DELETE` through `SELECT id FROM retailers` — under a `DELETE`-only policy every one of those `SELECT`s still returns nothing, so the sweep would keep deleting nothing *while a policy sat there making it look fixed*. `USING (true)` is a filter, not a widening: it names only the two backend roles, is `PERMISSIVE` so it ORs with the `authenticated`/`anon` policies instead of replacing them, and cannot grant a privilege — `kanchuki_app` still has no `DELETE`, because the `REVOKE` in `scripts/setup-role-separation.sql` is checked *before* RLS. The migration is guarded on both roles and on each table still existing (a `CREATE POLICY` naming a missing role is a hard error that would abort `prisma migrate deploy` in a brand-new environment) and is idempotent.
- **Proof (RLS half):** `purge-rls-policy.test.ts` re-derives the required set from `schema.prisma` + the migration history + both job sources and fails if migration 111's array drifts from it in **either** direction — a missing entry is a sweep that silently does nothing, a stale one is RC-029 returning. It also pins the three things that make the fix a fix: `FOR ALL` (not `FOR DELETE`), both roles named, and the role/table guards present. **Falsified five ways, each hitting exactly one assertion:** dropping `customer_interactions` from the array → the missing-tables check and the four-tables check; an invented `user_sessions` entry → the stale check; `FOR ALL`→`FOR DELETE` → the `FOR ALL` check; dropping `kanchuki_app` from the policy → the roles check; removing the role guard → the deploy-safety check. `purge-rls-live.test.ts` is the *executed* proof (opt-in via `PURGE_RLS_TEST_DATABASE_URL`, since no test in this repo touches a real database): it lifts the `CREATE POLICY` statement **out of the migration** — so it cannot drift from what will run — and on scratch tables with real RLS shows (a) no policy → `SELECT` returns 0 and the row survives silently, (b) a `FOR DELETE` policy → *still* 0 and the row survives, (c) migration 111's policy → the sweep sees the row and it goes; plus a case proving the cron's `audit_logs` **insert** raises 42501 without a policy (that failure is loud, unlike the deletes). Its extraction regex is asserted to yield the real DDL, so a bad parse cannot make the live run fail for the wrong reason.
- **Proof:** the gap was mechanically enumerable, and was: parse `schema.prisma` for models declaring `retailer_id` **without** a `references: [id]` relation to `Retailer`, then diff against every table the purge consumers name. 13 candidates, 6 purged, **7 orphaned**. The check became the test rather than a one-off audit — `apps/api/src/jobs/purge-soft-deleted.test.ts` → `RC-030 — every bare-\`retailer_id\` table has a purge decision` parses the schema at run time, resolves cascade reachability from the schema's own `onDelete: Cascade` relations to a fixpoint (which is why `product_videos` needs no cron delete — its `product_id` FK to products, migration 055, carries it away), and fails naming any bare-`retailer_id` table either job misses. **Falsified twice:** deleting the `promotions` sweep from the cron fails it with `expected [ 'promotions' ] to deeply equal []`; adding a new bare-`retailer_id` model to the schema fails **both** jobs' assertions with `expected [ 'test_orphan_table' ]`. A separate counter-test asserts `BARE_RETAILER_MODELS.length >= 7` so a broken parse cannot make the guard pass vacuously. `purge-retailer-now.test.ts` additionally asserts all 7 deletes are issued before the retailer row.
- **Prevention lesson:** for a denormalised `retailer_id`, make cleanup a **schema-driven** obligation rather than a copy-pasted line — the shipped guard fails when a bare `retailer_id` model is absent from either job, turning a silent retention bug into a red build. That is the mechanism the RESTRICT-FK tables never had either (they were caught by luck and by three separate bug reports); both lists are now derived from `schema.prisma` instead of trusted. Any new table with `retailer_id` and no FK is a purge-list change in the same PR, the way a RESTRICT FK already is — and the grant travels with it, per RC-029. The RLS half adds the third obligation: a table with `ENABLE ROW LEVEL SECURITY` on this path also needs an entry in migration 111, because a missing policy is indistinguishable from a working one at every layer except an executed query. The generalisable rule this session produced is that **a permission boundary and a silent filter are the same bug shape** — both make an operation succeed while doing nothing — so both need a check derived from the schema rather than a list someone maintains by hand.

## RC-026 — The personalization opt-out on /my-profile saved nothing and said nothing (a DPDP consent control failing silently)

- **Component:** `apps/web/src/app/api/passport/[...path]/route.ts` (the path allowlist and the exported verbs); `apps/web/src/app/(shopper)/my-profile/page.tsx` (the opt-out toggle)
- **Commit:** found 2026-09-17 while sizing `/my-profile` for phone/tablet; fixed the same day in `216a288a`
- **Symptom:** a shopper toggles “Personalization / profiling” off on `/my-profile`, the switch shows the new position, and nothing is persisted. No error is shown, no `pageerror`, and **no console output at all** — the failure is completely invisible from the browser, the server log, and the e2e suite.
- **Root cause:** a missing verb and a missing allowlist entry, each harmless alone.
  1. The page sends `PUT /api/passport/preferences`. The proxy’s `PASSPORT_PATHS` allowlist did not contain `preferences`, and it exported only `GET` and `POST` — so there was no handler for `PUT` and the request could only ever get a `405`.
  2. `fetch` **does not throw on a non-2xx response.** The handler’s `.catch()` only catches throws, so a 405 resolved as a normal promise, the `catch` never ran, and the component treated the rejected write as success. This is the half that made it a *silent* failure rather than a visible one.
  3. The API side was complete and correct all along (`GET` + `PUT /v1/public/passport/preferences`, including the profiling opt-out consent events). Only the web hop between them was absent.
- **Fix:**
  1. `route.ts` now has a single `forward(request, path, method)` shared by `GET`, `POST` **and** `PUT`. Previously each verb had its own copy of the body, which is precisely how `PUT` came to be missing — one more verb now means one line, not a duplicated function to forget.
  2. `preferences` added to the allowlist.
  3. The client checks `res.ok` and, on failure, **reverts the toggle and surfaces the error** rather than leaving the UI claiming a consent choice the server never received.
- **Proof:** 6 new route tests in `apps/web/src/app/api/passport/[...path]/__tests__/route.test.ts`, deliberately including the two verbs that already worked (`GET`/`POST`) because the shared-forwarder refactor touched them — a refactor that fixes one verb by breaking two others would otherwise pass. Plus an e2e test, `the personalization opt-out reaches the API instead of failing silently`, which polls the stub’s request log for `PUT /v1/public/passport/preferences` (polled, not sampled — the request lands after the UI settles).
- **Why the console check did not catch it (worth knowing):** the console-error capture added in the RC-025 pass was already live and stayed quiet, because a 405 is not a *failed resource load* — `fetch` resolved fine and the app swallowed it. Console capture only sees what the browser considers a fault, so it is not a substitute for asserting the request arrived.
- **Prevention lesson:** “it did not throw” is not “it worked”. Any handler that derives its error UI from `catch` alone treats every server-side rejection as success, and a `fetch` never rejects on 4xx/5xx. Consent controls need the opposite default: the UI must reflect confirmed server state, never the optimistic local intent. This is also the same shape as RC-025 — client, API, and model all present and correct, with the middle link missing — but here the consequence is a **DPDP-visible** defect: a shopper exercised a data-protection opt-out and the platform silently kept the older setting.

## RC-024 — E2E assertion sampled a cache-warm first paint, failing intermittently while the UI was visibly correct

- **Component:** `apps/web/e2e/customer-stores-directory.spec.ts` (the "signed-out visitor" test); the shared helper it exposed lives in `apps/web/e2e/support/responsive.ts`
- **Commit:** `32fdc097`
- **Symptom:** `expect(state.requests.filter((r) => r === 'GET /v1/public/stores').length).toBeGreaterThan(0)` failed on **one run in three** — in the same test whose assertion immediately above it (`Meera Sarees` visible) had just passed. Same file, same commit: 18/18, then 1 failed, then 19/19. A check that red-lights on a zero-code change is the most expensive kind of CI noise (same class as RC-019).

On a **cache-warm** run the server renders the page with **no network call at all**, so the store card is in the *first paint*; the client component's mount fetch is still in flight when the assertion reads the request log, which had `/v1/public/passport/me` (settled — the entry point cannot render without it) but not `/v1/public/stores`. On a **cold-cache** run the SSR fetch reaches the stub *before* the response is served, so the entry is always logged and the test passes. - **Proof:** **2 consecutive full-suite runs, 19/19** — the run type that exposed it (RC-019 established that a single `-g` run is not a valid signal).
- **Prevention lesson:** an assertion that reads a side-channel — a request log, a counter, a cache — is a **sample, not a synchronisation point**, and "the UI updated" does not imply "my observed side effect has already happened". Next's Data Cache makes this sharper: it is on disk, so a *previous* run can leave the server able to answer without touching your stub at all. When a page can render from a cached server render, poll the side-channel. Unrelated but worth knowing locally: that same cache can leave stub data ("Meera Sarees") in a developer's `.next/cache` after a test run — `.next` is never deployed, but a local dev server may serve it until the entry expires.

## RC-021 — Every real-phone login sends two different OTPs from two different MSG91 senders/templates

- **Component:** `apps/api/src/routes/auth.ts` (`POST /otp/send`), `apps/mobile/app/auth/phone.tsx` (`handleSend`)

- **Symptom:** entering a real phone number produced two SMS from two different senders (e.g. `CP-KCUKI3-S` "for KANCHUKI — Sejix Technologies", the DLT-registered template, AND `CP-DSHOTP-S` "--Dash", the MSG91 widget's own default flow template) — not a duplicate of the same message (that was already fixed by RC-015's re-entrancy guard), two genuinely different codes.

## RC-019 — Offline-fallback e2e test intermittently fails by reaching the real server

- **Component:** `apps/web/e2e/customer-collection.spec.ts` (`collection pages work offline via the service worker`, step 7)
- **Commit:** `7483b93f`
- **Symptom:** CI job `e2e-web` failed on `await expect(page.getByRole('heading', { name: "You're offline" })).toBeVisible()` — twice in a row (initial + retry #1) on run `34618428005`, then PASSED on the very next commit whose only diff was documentation. A check that red-lights on a zero-code change is the single most expensive kind of CI noise: it blocks merges, it trains everyone to re-run instead of read, and it hides real regressions in the same job.
- **Root cause:** the test simulated "no network" with `context.setOffline(true)` alone. That blocks the **page's** network stack, but the **service worker's own `fetch()`** is not reliably covered by it. When that fetch reached the still-running `next start` server, `/c/never-visited` answered with its real 307 redirect, the SW followed it and returned `/meera-sarees/festive-edit` — the cached copy of the collection page — so the precached `/offline` fallback never ran and the heading never appeared. Whether the SW slipped through was timing-dependent, which is exactly why the same commit could pass and fail. Two follow-on findings, both from traces: `context.route()` **does** intercept SW-originated *subresource* fetches but **not** the SW's *navigation* fetch, so aborting one URL (or even `**/*`) cannot make a navigation offline; and the SW target is the thing that must be offline — the page target being offline proves nothing about it.
- **Fix (shipped):** step 7 no longer navigates to an **uncached** URL. That assertion is removed as **not makeable deterministic from Playwright today**, and the spec carries a comment block recording the evidence. Three attempts were each disproved by instrumentation rather than assumed: (a) `context.route('**/*', route.abort)` — a trace showed the SW's own *navigation* fetch still reaching the running `next start` and receiving the real 307, so aborting cannot make a navigation offline; (b) gating on the SW target's `navigator.onLine === false` — a **false positive**: the worker reported offline while its navigation still landed on the collection page; (c) stubbing the worker's global `fetch()` **and** disabling `navigationPreload` (the browser's second, independent path for document navigations) — still ~1-in-3, and on failing runs `caches.match('/c/never-visited')` was a **MISS while `fetch` was stubbed**, proving the response came from Chromium's handling of the SW-controlled navigation, not the worker's routing or its caches. Step 7 now asserts the layer that *is* deterministic: a new `expect.poll` precondition proves `/offline` is actually in the precache (so a missed install-time precache fails in 10s naming the real cause instead of a 15s "element not found" timeout at the last assertion), and the cached document is then read directly and asserted to contain "You're offline".
- **Proof:** `playwright test -c playwright.customer.config.ts` → 3/3 green across **3 consecutive full-suite runs** (the run type that exposed the flake; single-test `-g` runs were never a valid signal here); `apps/web` `tsc --noEmit` clean; repo `pnpm lint` exit 0 (6/6 tasks).
- **Prevention lesson:** `context.setOffline(true)` is not a switch for "the network is gone" — it does not reliably cover service-worker-originated requests, and it is the *service worker's* view of the network that the offline fallback depends on. Do not trust a passing run to mean the precondition held — this test passed in isolation and failed in the full suite, so a green `-g` run proves nothing. And when an assertion genuinely cannot be made deterministic at the layer it needs, **remove it and assert the layer below** rather than shipping a 1-in-3 flake: a check that red-lights on a zero-code commit costs more than the coverage it buys, and the honest gap belongs in a comment next to the code.

## RC-017 — AI Studio Shoot always generates the first style regardless of tap

- **Component:** `apps/mobile/src/components/product-detail/ProductStudioModal.tsx`
- **Commit:** `faf2d64d`
- **Symptom:** retailer taps Product/Model tab, taps any style row — the tapped row never shows selected, only the first row does, and Generate always produces the same output regardless of what was tapped.
- **Root cause:** a `useEffect` re-selects `activeList[0]` on every dependency change, and `activeList` (`styles.filter(...)`) is a **new array every render**. ## RC-011 — Switch-Plans request times out because the server's Razorpay call has no timeout

- **Component:** `apps/api/src/routes/billing/billing-helpers.ts` (`razorpay()`), `apps/mobile/src/lib/api/billing.ts` (`subscribe`/`cancel`)
- **Commit:** `54970c5a`
- **Symptom:** switching plans showed "Error — Request timed out (/v1/billing/subscription). Check that the API server is running at https://api.kanchuki.app and try again." — a client-side timeout message that made it look like the API was down.
