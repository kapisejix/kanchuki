## RC-042 — the keyboard inset is a platform behaviour **every** overlay and screen had to apply and **none** did, because it lived as a convention instead of as a component — and no desktop browser can show it missing

- **Component:** `apps/web` — 18 `fixed inset-0` overlays holding text fields (`AIStylist.tsx`, `CustomerConsentModal.tsx`, and the admin dialogs in `ai-providers`, `commission`, `festivals`, `customers`, `retailers/[id]`, `operations/pending`, `database/query`, `team-members`, `photo-cleanup-test/EffectsCatalog`) · `apps/mobile` — **no `KeyboardAvoidingView` anywhere in the app** while 36 screens in `app/` own a `TextInput` (all 36 now route through the wrapper) · found 2026-09-25 while working the launch board.
- **Commit:** fixed in this session. The shared primitives are `apps/web/src/components/Sheet.tsx` (+ `apps/web/src/lib/keyboard-inset.ts`, the measurement) and `apps/mobile/src/components/KeyboardScreen.tsx`.
- **Symptom:** on iOS, focusing an input inside a bottom-anchored sheet put the input **behind the keyboard** with no way to scroll to it — the AI Stylist query box, the admin dialogs' lower fields, and (on every screen) the bottom-most field of a long form. Content that is reachable on a desktop browser and unreachable on the phone the product ships on. Nothing logs, nothing throws, no test goes red: the layout is *valid*, it is simply covered.
- **Root cause:** iOS Safari does not reflow `position: fixed` for the software keyboard — the layout viewport keeps its full height and the keyboard just paints over the bottom of it (Android is the opposite: it resizes the layout viewport). Every overlay therefore needs the same correction, applied per instance, and the correction was **nowhere**: it was a platform behaviour that lived in nobody's head. That is the RC-034 shape (a rule that must be repeated, therefore eventually not repeated) with the enforcement inverted — RC-034's copies failed **open** and leaked access; these failed **silent** and hid input. The absence was undetectable by reading a single file, because a file that forgot the inset looks exactly like a file that never needed one.
- **Why the fix had to be a component, not 47 careful edits:** the rule is *"every fixed overlay holding a field, and every screen with a field, must correct for the keyboard"*. Correcting each site once leaves the next overlay free to be born missing it, and the failure is invisible — so the enforcement went where the counting can be derived instead: `apps/web/src/app/admin/__tests__/keyboard-inset.test.ts` derives every admin overlay holding a text field from the sources and fails until each is adopted or excluded **with a reason**, and `apps/mobile/__tests__/keyboard-screen-adoption.test.ts` bans the raw `KeyboardAvoidingView` from `app/` entirely (one documented exemption) plus the re-derived `Platform.OS === 'ios' ? 'padding' : 'height'` ternary in any screen.
- **The measurement problem, and the false green it creates:** the inset can only be read from `window.visualViewport` (`height` shrinks, `offsetTop` moves), never from `window.innerHeight`. **No desktop browser can exercise it** — Chromium *and* desktop WebKit both report `visualViewport.height === window.innerHeight` with no software keyboard, so the computed inset is always `0` and the fixed-path branch never runs. A perfectly green desktop run is therefore **no evidence at all** about the device behaviour. What the suites pin is the *mechanism* on a faked viewport; the device pass is recorded separately as the board's **§7B.9** rather than claimed here.
- **Prevention lesson:** two rules. (1) **A platform behaviour that every instance must apply is a component's job** — if the correct fix is "remember to add this line in each of N places", the bug is already scheduled, and the guard must *derive* the N from the sources rather than list it. (2) **A guard must be falsifiable on the machine that runs it**: the desktop inset being permanently `0` means any test asserting "the input is visible" passes whether or not the fix exists (an `<img>`/`<input>` keeps its box when it is covered), which is the RC-025 failure shape — described in one place, verified in none. State which environment cannot produce the evidence, and where the real check lives.
- **Proof:** `apps/web` — `lib/__tests__/keyboard-inset.test.ts` 19 (measurement: no viewport / non-finite / `scale > 1` / negative clamp / rounding); `components/__tests__/Sheet.test.tsx` 10 (inset applied only when open, `maxHeightVh` cap, **zero listeners while closed**, backdrop click, closed-state layout has no inline style); `AIStylist.test.tsx` 3; `EffectsCatalog.test.tsx` 3; the adoption derivation guard 21 (a case per adopted file + a case per exclusion, both `it.each`). `apps/mobile` — `KeyboardScreen.test.tsx` 8 (incl. the Android branch, read by re-importing the module with `Platform.OS` swapped, since the constant is resolved once at module load) and the adoption guard 8. Falsified on both sides, each red for the right reason and restored. Web: deleting `Sheet`'s overlay inset; deleting the `open` gate so the hook subscribes while closed; a new `admin/__falsify__/page.tsx` overlay holding an input (the derivation named it); an excluded lightbox turned into a field-holder (its own exclusion arm); `AIStylist` reverted off `<Sheet>` (the web-wide hook-scan arm). Mobile: collapsing `'height'`→`'padding'` (the Android branch — `expected 'padding' to be 'height'`); a raw `KeyboardAvoidingView` added to a temp screen (named by the derivation); a screen re-deriving the ternary **through** the wrapper's prop (that arm alone red, which is why the two arms are separate); a wrong-depth import; and a render with its import deleted. Web **392/392** (49 files), `tsc --noEmit` + `next lint` clean; mobile **123/123** (20 files), `tsc --noEmit` + `eslint` clean.
- **Not verified:** real-device behaviour on iOS **and** the Android arm of `KeyboardScreen` (a different mechanism — `height`, because Android reflows the layout viewport). Both are procedures in the board's §7B.9, not claims.

## RC-043 — eleven copies of one test helper, two of them broken, and **nothing tested the helper** — so a guard that could not fail read exactly like a guard that passed

- **Component:** `stripComments` (or an inline `code()`) in **eleven** source-scanning guards. First pass (found 2026-09-25 while falsifying RC-041's fix): `apps/api/src/routes/{admin-access,load-test}.test.ts`, `apps/api/src/lib/retired-tryon-guard.test.ts`, `apps/api/src/jobs/purge-rls-policy.test.ts`, `apps/web/src/lib/__tests__/deep-links.test.ts`, `apps/mobile/__tests__/keyboard-screen-adoption.test.ts`. **Second pass, before these docs were finalised** — a grep of the regex *shape* rather than of the note that said "six": `apps/api/src/jobs/referral-{accrue,qualify,payout}.test.ts` and `apps/api/src/routes/admin/admin-referral-monitor.test.ts` (×2 in `referral-payout.test.ts`, the second one inline inside a single test).
- **Symptom:** two of the six stripped comments with the naive `.replace(/\/\/[^\n]*/g, '')`, which treats **every** `//` as a comment opener — including the `//` in `intent://`, `https://` and `kanchuki://`. On any line mentioning one of those it deleted the rest of the line: precisely the text the surrounding arms search for. Those arms therefore reported "nothing found" for the same reason they would have with the banned thing present. The other four were not identical either — two used `(^|\s)\/\/`, which misses a comment that follows code with no space (`x();// idm-vton`), so a banned string written there survived the strip and the guard failed later with a message that made no sense out of context.
- **Root cause:** a **test-helper snippet with no owner**. Each guard needed the same 5 lines, each wrote its own, and nothing tested any of them — the helper was invisible to every check because it *is* the check. It is the same shape as RC-041 and RC-034 (a rule written out per call site), with a worse consequence: the value duplicated was the correctness of the guard itself. Nothing failed, because a broken stripper only ever *removes* text — its output on a clean file is byte-identical to its output on a broken one.
- **Why it was invisible:** the two possible verdicts are the same string. "The scan found nothing" is what a working guard says about a clean tree **and** what a vacuous guard says about a dirty one. No assertion could distinguish them without a mutation, which is why it survived: it was found only by typing a real `intent://` link back into a page and watching the RC-041 arm stay green.
- **Measured, both directions, same violation untouched:** with the naive stripper restored **and** a hand-written `intent://…package=z;end` link appended to `apps/web/src/lib/keyboard-inset.ts`, `deep-links.test.ts` reported **10/10 passed**. With the stripper fixed and that link still in place, the same suite failed with `expected [ 'lib/keyboard-inset.ts' ] to deeply equal []`. The guard's ability to fail was the thing that had no test.
- **Fix:** `packages/shared/src/testing/strip-comments.ts` — one implementation, exposed as the `@kanchuki/shared/testing` subpath so it is physically impossible for it to reach an app bundle (`exports` maps only `./testing`, and no runtime module imports it), with the reasoning for each clause of the regex written at the function. All eleven migrated, so the regex now exists in exactly one file — and that is now a **checked** fact rather than an assertion: grepping `(^|[^:])` or `[\s\S]*?\*/` outside `packages/shared/src/testing/` returns nothing. Two clauses carry the fix: `(^|[^:])` keeps a `//` that follows a `:` intact (the scheme case), and `$1` returns the seam character — dropping it would join the two sides of the cut and could invent a token that matches, or hide one that should have.
- **The second pass also found that the two passes do not commute, which the first six had all been getting right by luck.** A line comment that itself contains `/*` (real case — a route header reading `// mounted under /v1/public/*;`) makes a block-first pass open a block *inside the comment* and run to the next real `*/`, eating the live code between them, so a scan over the result is quiet for the same reason a broken detector is quiet. Two of the five late-migrated callers had already hit this and stripped line-first; the order is now an explicit `'line-first'` argument on the shared helper instead of a convention each file re-derived, and both orders have their own arms (block-first eats `const keep = 1;` in the constructed case, line-first keeps it, and the two agree when neither rake is present). **The rake then fired for real on the first run after the migration:** `apps/api` resolves `@kanchuki/shared/testing` from the built `dist/` (the RC-035 trap — gitignored, therefore stale), so the new argument was silently ignored by the one-argument build still on disk, block-first ran, and `admin-referral-monitor.test.ts` went red with the import line eaten out of the stripped source. Rebuilding the package fixed it. A signature change to a `dist`-consumed package needs a rebuild before any result is believed.
- **What this audit got wrong on its first pass — kept, not tidied away:** it inventoried **six** call sites, migrated them, recorded that the regex then lived in one file, and added that the remaining guards "read `specific named files` rather than stripping and scanning, so they have no stripper to be broken". Five more call sites were doing exactly that (all in the correct form, so nothing broken survived), which makes the paragraph both an undercount and a wrong generalisation. The failure shape is the bug's own, one level up: **an inventory nothing re-derives drifts, and a hand-written list is not evidence.** It was caught only because the docs were being finalised and the claim was worth a command — which is the durable fix: keep completeness in the grep, not in the prose.
- **Correction found while writing the docs for it:** the helper's first documented limit claimed `label: // note` is *not* stripped. The suite refuted it on the first run — the character before `//` is the space, so it *is* stripped; only a `//` **immediately** after a `:` is exempt. The limit is now stated narrowly and the distinction has its own assertion, because a doc that overstates a limitation is how the next person concludes their case is uncovered when it is not.
- **The fourth member of this family in this repo:** `apps/mobile/__tests__/keyboard-screen-adoption.test.ts`'s local helper carried a docblock that *rationalised* the damage — "a truncated line only ever makes the guard *quieter* for that one line, never wrongly red". Quieter is the entire failure mode; the comment asserted the bug was acceptable. Cite it when the next person proposes accepting a guard limitation in a comment.
- **Proof:** `packages/shared/src/testing/strip-comments.test.ts` **15/15** (was 12; +3 for the order), including the arm that reproduces the bug by name (`keeps a real link when a commented-out one sits above it` — one `intent://` in, exactly one out) and its inverse (`drops a commented-out link entirely`). Consumers re-verified after migration: `admin-access` 12/12, `load-test` 54/54 (including its "scans … not vacuously" arm), `retired-tryon-guard` 8/8, `purge-rls-policy` 11/11, `keyboard-screen-adoption` 8/8, `deep-links` 10/10, and the five late-migrated api suites 151/151 together (`referral-accrue`, `referral-qualify`, `referral-payout` 57, `admin-referral-monitor` 34). **Falsified 7 ways, each red for the right reason and restored:** reverting the shared stripper to the naive form → the shared suite red **and** the web source arm vacuously green with a link on disk (the bug, reproduced on demand); the correct stripper with that link untouched → red, naming the file; dropping the `'line-first'` argument at `admin-referral-monitor` → red, the import line gone from the stripped source (**the rake, on demand**); changing the helper's default order → the block-first arm red (`expected '…const keep = 1; …' not to contain 'const keep = 1;'`). Suites: shared **62/62**, api **1432 passed / 5 skipped**, web **402/402**, mobile **123/123**; `tsc` clean ×4, web `next lint` clean, api `biome check src/` clean (332 files).
- **What the audit did NOT find, stated as a limit rather than a clearance:** the remaining source-scanning guards read *specific named files* rather than stripping and scanning, so they have no stripper to be broken — they can be wrong, but not in this silent way. Treat that as true **as of the shape-grep above**, not as a standing claim: the first version of this bullet said the same thing about guards that were, in fact, stripping. The honest form of the sentence always carries its command.

## RC-041 — the web `/join` bridge hardcoded the wrong Android package in its `intent://` deep link, so "Open with Android app" could never open Kanchuki — **fixed 2026-09-25** (found the same day while building §5B.1)

- **Component:** `apps/web/src/app/join/page.tsx:54` (`openInApp = 'intent://join?token=…#Intent;scheme=kanchuki;package=in.kanchuki.app;end'`) · the real package is `app.kanchuki.retailer` (`apps/mobile/app.json:11` `android.package`, `:29` `ios.bundleIdentifier`) · found 2026-09-25 while building the `/for-retailers` referral-capture page (§5B.1), which reuses the same `intent://`/`kanchuki://` bridge pattern — cross-checked the package name against `app.json` before reusing it and found the existing copy was already wrong.
- **Status: fixed.** Recorded as found-not-fixed while building §5B.1 (a different page, pre-existing, not what that task was for), then fixed in the same session once it was picked up. `apps/web/src/app/for-retailers/page.tsx` had already avoided the error by using the scheme-only `kanchuki://onboarding?ref=…` form.
- **Symptom:** on Android, tapping "Open with Android app" on the staff-invite bridge page (`/join?token=…`) fires an `intent://` URI whose `package=` names an app that does not exist on the device (or on the Play Store, which isn't live yet either). Android falls through to its default intent-resolution behaviour rather than opening Kanchuki. The plain `kanchuki://` scheme link right above it ("Open in Kanchuki app") still works, since a custom URL scheme has no package to get wrong, so this only breaks the fallback a reviewer is less likely to test.
- **Root cause:** the `intent://` URI was written by hand with a package name never cross-checked against `app.json` — the two files (`apps/web/src/app/join/page.tsx`, `apps/mobile/app.json`) share no source, so a typo/guess in one has nothing to catch it at build time; neither `apps/web` nor `apps/mobile` tsc fails regardless.
- **Fix:** `apps/web/src/lib/deep-links.ts` (new) became the only place the scheme and package existed in `apps/web`, and every link in `apps/web` is built through it — `APP_SCHEME` / `ANDROID_PACKAGE`, `appLink(host, params)` → `kanchuki://…`, `androidIntentUrl(host, params)` → `intent://…#Intent;scheme=…;package=…;end`. **All four** hand-written call sites migrated, not just the broken one: `join/page.tsx` (both links), `for-retailers/page.tsx` (the `?ref=` link), `social/connect/page.tsx` (the OAuth `code`/`state` callback). **Extended the same session:** the constants and both builders moved to `packages/shared/src/constants/app-identity.ts` (`@kanchuki/shared`), because auditing this fix found a **third** hand-written copy — `apps/api/src/lib/staff-invite.ts` built `kanchuki://join?token=…` itself — and the mobile app is the third consumer. Web's module is now a pure re-export (holding no literals at all), and the API builds through `appLink('join', { token })` (byte-identical output: a base64url token percent-encodes to itself). `apps/mobile/app.json` cannot be imported from anywhere — Expo resolves the manifest before any TypeScript runs — so the value was *written* twice and a test held them together; **later the same day it stopped being written twice at all**: `app.config.js` → **`app.config.ts`** now imports the constants, from the shared module's *source* (`require('sucrase/register/ts')` + the `@kanchuki/shared/constants/app-identity` subpath, whose `default` condition points at `src/` deliberately, so it can never silently resolve to a stale build). The reason it cannot import the built package was measured, not assumed: `dist/` is gitignored and the release path (`pnpm install` → `expo prebuild` → Gradle) never builds it, so `require('@kanchuki/shared')` died with `Cannot find module …/dist/index.js` *before Gradle ran* — an unbuildable app rather than a dead link. `app.json` no longer holds any of the three fields, and what `expo prebuild` resolves is now asserted by evaluating the real config through `@expo/config` — `apps/mobile/__tests__/app-config.test.ts`, the only arm that can see a config which fails to load — with the source-reading arms inverted to "the manifest carries no copy" and "the config imports it and types no literal".
- **Prevention lesson:** the same shape as RC-034's classification lists and RC-027's engine strings — a value duplicated by hand across two files/packages with no single source and no test pinning them together. The durable fix named here was "a shared `ANDROID_PACKAGE` constant + a test that greps `app.json` and asserts every `intent://package=` string in `apps/web` matches it", and that is what was built: the constant now exists and `lib/__tests__/deep-links.test.ts` asserts it equals `app.json`'s `expo.scheme` / `expo.android.package`, that no file under `src/` other than the module contains `intent://`, `kanchuki://` or a `package=` literal, that the package literal appears in exactly one file, and that `in.kanchuki.app` appears **nowhere**. Hand-written links are now structurally impossible without failing a test.
- **Proof:** `packages/shared/src/constants/app-identity.test.ts` (**11/11**, the canonical pin: manifest, merge-only config, builders, and every package/bundle line in the two live operator docs) plus `apps/web/src/lib/__tests__/deep-links.test.ts` — **10/10**. Behavioural: the manifest pin (`APP_SCHEME === expo.scheme`, `ANDROID_PACKAGE === expo.android.package`), the package-syntax check, both builders' exact output, absent params omitted rather than emitted empty, `&`/`=`/`#`/`/` percent-encoded (the `code`/`state` params come from a Meta redirect and are the ones that can carry them), multi-param joining. Structural: the four source-scan arms above. **Plus the pin that was actually missing** — `apps/web/src/app/join/__tests__/page.test.tsx` had asserted the `kanchuki://` link and *never* the `intent://` one, which is exactly why this shipped; it now asserts the whole URI including `package=app.kanchuki.retailer`.
- **Falsified 2 ways, and the first one found a defect in the guard itself.** Changing `ANDROID_PACKAGE` by one character (`retailer` → `retailers`) went red on the manifest pin, both builders **and** the join-page assertion. Then, restoring the module and typing the old bad `intent://` string back into `join/page.tsx`, the page assertion went red — **and both source-scan arms stayed green**, which they should not have. Cause: the guard's comment-stripper was the naive `.replace(/\/\/[^\n]*/g, '')`, and `intent://` *contains* `//`, so the stripper deleted the very string the arms search for. Every structural arm in that file was **vacuously green**. Fixed by only treating `//` as a comment when it is not preceded by `:` (`.replace(/(^|[^:])\/\/[^\n]*/gm, '$1')`, with the reason spelled out in the code), after which both arms fired and named `app/join/page.tsx`. **This is the third vacuous/flawed guard found by mutating rather than reading it in two days** (RC-039's F7 resolved its own path from a literal filename; here a regex ate its own subject) — the shared lesson is that a guard's *ability to fail* has to be tested, not assumed, because a green arm reads identically whether the rule holds or the detector is broken.
- **Web 402/402** (50 files), `tsc --noEmit` clean, `next lint` clean. No migration, no `apps/mobile`/`apps/api` file.

## RC-040 — JSON-LD was injected with `JSON.stringify` into `dangerouslySetInnerHTML`, and `JSON.stringify` does not escape `<`, so a retailer's own `shop_name` could close the `<script>` tag and run markup on **every** storefront page (stored XSS)

- **Component:** `apps/web/src/app/[store]/lib/store-seo.ts` (`ldJson`) · consumers `apps/web/src/app/[store]/page.tsx`, `apps/web/src/app/[store]/categories/page.tsx` (both shipped with raw `JSON.stringify`), plus the new `[collection]` / `[collection]/product/[productId]` JSON-LD added by §7A.2 · found 2026-09-24 while working the launch-readiness board (§7A.2).
- **Commit:** fixed in this session. The store + categories pages had been shipping the unescaped form; the two other surfaces were caught before their first commit.
- **Symptom:** none that monitoring could see — the pages render correctly for every well-formed store, which is every store in production. The trigger is data, not code: a retailer whose `shop_name` (or a product name / category in the `ItemList`) contains `</script>` closes the JSON-LD script element, and everything after it is parsed as markup — `<script>alert(1)</script>` runs with the storefront's origin. Stored, because the value is saved once at onboarding and served to every visitor afterwards.
- **Root cause:** **`JSON.stringify` is a serialiser, not an HTML escaper, and `dangerouslySetInnerHTML` is an HTML sink.** The two were used together with no escaping step in between, which is safe for every value except the one that matters. `JSON.stringify` deliberately leaves `<`, `>`, `&` and `/` as-is (they are valid inside JSON strings), and the HTML parser does not know it is inside a JSON-LD block: it ends the script element at the first `</script`, **case-insensitively** — so `</SCRIPT>` and `</script >` break out too. This is the OWASP XSS-prevention rule for `application/ld+json` verbatim: JSON inside a `<script>` must have at least `<` escaped, and the conventional transform is `<` → `\u003c` (unambiguous in the document, identical after `JSON.parse`).
- **Why it survived review:** three locally-correct readings. The data is **our own** (a retailer's profile, not a visitor's input), so the annotation read as "trusted" — but the retailer is an untrusted principal relative to the storefront visitor; `RETAILER-INPUT → OUR PAGE → ANOTHER USER` is stored XSS by definition. The `biome-ignore lint/security/noDangerouslySetInnerHtml: JSON-LD from our own retailer data, no user input` comment **asserted safety where the check would have fired**: the lint rule was doing its job, and the suppression stated the opposite of the truth. And the output *looks* escaped — it is full of `\"` and `\\` — so nobody re-checks whether it also escaped `<`.
- **Fix:** one helper, `ldJson(data) = JSON.stringify(data).replace(/</g, String.raw`\u003c`)`, used by all four JSON-LD call sites (store, categories, collection `ItemList`, product `Product`/`Offer`). Escaping every `<` also covers `<script`/`<!--`; `>` and `&` are not needed here because only `<` can start the sequences that end a script element. The `biome-ignore` is kept — the sink is still a sink, and the data is now escaped rather than trusted.
- **A near-miss in the fix itself, and how it was caught:** the first written form was `.replace(/</g, '\u003c')` with **one** backslash, which in a JS string literal is the single character `<` — i.e. a no-op that replaced `<` with `<` and looked identical in the diff to the correct form. `store-seo.test.ts` was run before the change was committed and went **red** on exactly this, which is why the escape is now the `String.raw` template (a literal `\u003c`, no escape-processing layer in between) and the test asserts the **absence of `</script>` in the output string**, not merely that the page renders.
- **Proof:** `store-seo.test.ts` **3/3** — the escape arm asserts `out` does not contain `</script>` **and** `JSON.parse(out).name` still equals the original raw string (escaping must not change the value), plus Offer/AggregateOffer/no-offer and `ItemList` numbering. **Falsified:** reverting `ldJson` to bare `JSON.stringify` turns the escape arm red (`expected '…' not to contain '</script>'`), the two other arms stay green. Web **326/326**, `tsc --noEmit` clean.
- **Prevention lesson:** **every HTML sink needs its own escaping rule, and "our own data" is not one of them** — the trusted/untrusted boundary is *between principals* (retailer vs. visitor), not between the database and the page. The mechanical checks: a `dangerouslySetInnerHTML` on `<script type="application/ld+json">` must route through a helper that escapes `<`, and any suppression comment on that lint rule must name the **escaping function**, never the provenance of the data. Corollary from the near-miss: a security assertion that only checks the *rendered result* cannot see a no-op escape — assert the dangerous substring is **absent from the serialised string**, which is what makes a one-backslash mistake fail.

## RC-039 — A test can outlive its own fixture: the fixture was one module-level object whose arrays `beforeEach` swapped, so a timed-out test wrote into the **next** test's state and the failure surfaced as a plausible wrong number in an unrelated assertion

- **Component:** `apps/api/src/routes/admin/admin-referral-monitor.test.ts` (prisma stand-in + `resetState`/`retireState`/`freshState`) · the same amplifier is present, unfired, in `apps/api/src/jobs/referral-payout.test.ts:220` (`resetState` reassigns `prismaState.*` on one shared object)
- **Commit:** found 2026-09-24 while chasing an intermittent `admin-referral-monitor` failure under the full parallel suite; fixed in the same session (test-infra only, no production code changed).
- **Symptom:** intermittent, roughly 1 full-suite run in 2–3, never in isolation and never in the same place twice:
  ```
  FAIL src/routes/admin/admin-referral-monitor.test.ts > GET /referral/overview > excludes FAILED batches from committed money
  AssertionError: expected 30000 to be +0
  ```
  The failing test seeds a single **FAILED** `20_000` payout and asserts `paid_out_paise === 0`. It read `30_000`, which is the *other* overview test's **PAID** row — so the failure reads as `GET /referral/overview` summing FAILED batches into committed money. It does not: the route was never wrong, and the number it was accused of was never in its input.
- **Root cause (two layers, and the first one is only a trigger):**
  1. **Trigger — a per-test dynamic import of the whole module graph.** This was the only file in 96 that built its app as `await Promise.all([import('fastify'), import('../../plugins/error-handler.js')])`, inside each test. Cheap alone; on a saturated worker the import exceeded vitest's 5s test timeout. Now static imports like every other suite.
  2. **Amplifier — the fixture was one object whose arrays were replaced.** `state` was a module-level `const` and `beforeEach(resetState)` did `state.payouts = []` (etc.). **Vitest abandoning a timed-out test does not cancel its promises.** `build()` resolved afterwards, the abandoned continuation ran its `seedConv`/`payouts.push` lines, and because `state` is a single object whose arrays had just been swapped, those writes landed in the **next test's freshly reset fixture**. Hence `30_000`.
  The two layers are independent: the leak is harmless without a timeout, and a timeout is harmless when each test owns its own fixture. Both are now addressed.
- **Why it survived review:** every locally visible reading is correct. The route's assertions are right; the failing test's seed is right; the mock is right; and the flake *looked* like a concurrency bug in the route, which is the kind of finding that gets "fixed" by loosening the assertion. Nothing in the file names the real invariant (a test's fixture must not be readable by the next test), and no assertion could see it — a leaked row is not distinguishable from a seeded one at read time.
- **Fix (two halves — and the first half, shipped alone, changed nothing):**
  - **Ownership (the actual fix):** the fixture became `let state: Fixture` swapped whole — `resetState()` is now `state = makeState()`, and a test's first statement is `const st = freshState()`. A late write then goes into the abandoned test's **own, now-unreferenced** object, which the next test cannot see at any timing.
  - **Retiring (the amplifier's alarm):** `afterEach(retireState)` freezes the retired fixture's arrays, so a late write **throws** (`Cannot add property 5, object is not extensible`) inside the abandoned promise chain instead of landing silently. Frozen *without* ownership this does nothing — it freezes arrays the next `beforeEach` immediately replaces, which is exactly why the freeze shipped first, was tested, and **did not stop the flake**.
  - **Guards (F6–F8):** F6 replays the mechanism deterministically (`abandoned`/`next` fixtures must be different objects, and the late write must throw); F8a/F8b pin the **wiring** F6 cannot see; F7 is a source scan asserting no test body writes the shared pointer.
- **Two guard defects found while proving it — both were green in their own mutant, which is the only reason they were caught:**
  1. **A guard that located itself by a literal filename.** F7 read `join(HERE, 'admin-referral-monitor.test.ts')`, so injecting a bare `state.payouts.push(…)` into a *copy* of the file left it green — it had scanned the original. Now `fileURLToPath(import.meta.url)`, i.e. always this file. Any guard that names its own path is one rename away from silently scanning something else.
  2. **A guard that pinned a function without its wiring.** F6 calls `retireState()` itself, so **deleting `afterEach(retireState)` left the suite at 32/32 green**. Measured, not assumed: the F6 comment first claimed the deletion would turn it red, and the experiment disproved the comment. F6 keeps the function half; F8b (a later test reading a fixture captured by an earlier one) covers the registration.
- **Proof:** `admin-referral-monitor.test.ts` **34/34** (was 32; +F8a/F8b, +F7 rewritten). Falsified three ways, each red for its own reason: **(A)** `resetState` back to clearing arrays on one shared object → F6 + F8b red (`expected [] not to be []` — the message itself shows one array); **(B)** `afterEach(retireState)` deleted → F8b red only (`expected false to be true`), F6 correctly stays green; **(C)** a bare `state.payouts.push(…)` in a test body → F7 red, naming the call. Full API suite **1353 passed / 5 skipped (1358), 0 failed, twice consecutively** under the default parallel run — the first clean back-to-back runs this file has had. `tsc` + biome clean.
- **Follow-up the same day (the margin, not the leak):** the stress run above also failed two *other* files with plain `Test timed out in 5000ms` — `lib/studio-shoot.test.ts` (both concurrent runs) and `routes/admin.login.test.ts` (one) — neither with a shared fixture. Both got explicit per-test timeouts, sized from measurements: `studio-shoot`'s pipeline tests are slow **by construction** (they drive the real poll loop, so each mocked poll costs a real 1 s `POLL_INTERVALS_MS` sleep: 1 mocked poll ≈ 1016 ms, a two-step pipeline ≈ 3.0 s, the A/B comparisons ≈ 4.5 s — a **443 ms** margin against the 5 s default), and `admin.login`'s first test carries the file's cold start, measured at **403 / 462 / 480 ms** across three fresh runs after a first sighting of 1449 ms that turned out to be **load rather than its own work**. Because contention is not reproducible on demand here (a second double-suite run died with `ERR_IPC_CHANNEL_CLOSED`), the guards were proven against a tiny **global** default instead — `--testTimeout=1000` / `--testTimeout=100` still pass, which is impossible unless the per-test option overrides it.
- **Prevention lesson:** **a test fixture has a lifetime, and nothing in vitest enforces it** — an abandoned test is not a cancelled one, so any per-test state reachable by identity can be written by the test that just gave up. Corollary for the trigger side: **a test whose cost is dominated by something other than assertions (a real sleep, bcrypt, a cold module graph) has a timeout budget, not a speed** — and a budget that looks comfortable on a quiet laptop is 0% headroom on a loaded CI box. Measure the margin, and make it explicit for the tests that have little. The check is mechanical: per-test state must be *owned* (created per test, reached only through a per-test binding), never *shared and cleared*. The second lesson is about the guards themselves: **a guard is only as good as its mutant** — a source scan that resolves its own path from a string, or a mechanism test that supplies its own precondition, will report green while the wiring it exists to protect is gone. Both failures here were found by running the mutation, not by reading the code.

## RC-038 — `SubscriptionPayment.status` advertised `refunded` in its own column comment and nothing in the repo could write it, so three consumers asked "was this month paid for?" — and one of them documented the impossible behaviour as a feature

- **Component:** `packages/db/prisma/schema.prisma:1010` (`status String // success | failed | refunded`) · `apps/api/src/routes/billing/billing-webhook.ts` (no `refund.*` case existed) · its three consumers: `jobs/referral-accrue.ts` (T6), `jobs/referral-qualify.ts` (T5), `routes/admin/admin-commission.ts` (§42)

- **Symptom:** *none observable* — which is the whole finding. Reading the consumers shows careful, whitelist-based code; reading the schema shows a status enum that mentions refunds; reading §42 shows a refund behaviour that "already works". All three readings are locally correct, and no test can fail on an event nothing emits. Only `refund.processed`; `created`/`failed` do not mean money moved back. Partial refunds are logged and not applied (owner decision 2026-09-24: a plan charge is refunded in full or not at all; a partial would need a `refunded_amount` column, migration 117, and a pro-rata rule).

T5 gained 2 (28/28). Full API 1349/1354 (5 skips), tsc + biome clean.
- **Prevention lesson:** **when a column comment or file header enumerates values a system can reach, the enumeration is a claim about writers, and nothing tests it.** A consumer's whitelist is not evidence that the other cases are impossible — it is evidence that only one case was ever observed. The check is cheap and belongs in review: for every literal in a status/enum comment, grep for a write of it; a value with readers and no writer is either dead documentation or an unbuilt feature, and the two are indistinguishable from the read side. Second-order rule this adds: **a comment that describes behaviour triggered by an event no code emits must say so** — "a refunded payment reduces the pool" and "a refunded payment would reduce the pool, but nothing writes `refunded`" are the same sentence to a maintainer and opposite statements to an operator. Same family as RC-025/RC-031: the guard or contract exists as *text*, in a place no test reads.

## RC-033 — The billing webhook collapses `subscription.completed` into `Subscription.status = CANCELLED`, so "finished its paid term" and "churned" are the same row — and T5's clawback branch now makes a money decision on it

- **Component:** `apps/api/src/routes/billing/billing-webhook.ts` (lines ~178-188, the `case 'subscription.cancelled': case 'subscription.completed':` fallthrough) · consumed by `apps/api/src/jobs/referral-qualify.ts` (T5)
- **Commit:** found 2026-09-22 while building T5. **Fixed 2026-09-24 in `72d3806d`** (owner ruling — see "Resolution" below). Everything from here to that bullet is kept **verbatim as the state at finding time**, including the "why deferred" reasoning and the reading of T5's decision; the ruling **revises** the latter.
- **Resolution (2026-09-24, owner):** the deferred owner decision came back **"a completed term is not churn."** The defect was fixed rather than re-documented, and the ruling overturns this entry's own "why the T5 decision is nevertheless CORRECT" argument — the argument was defensible on the spec's literal wording (*sustained paid **and** active*), but it priced a *successful, fully-paid* retailer as a churn and made the referrer's already-accrued commission the collateral. **The irreversibility is what decided it:** `CLAWED_BACK` has no undo (§11 / RC-036), so the strict reading buys nothing and costs an unrecoverable payout, while the lenient one leaves the accrual merely *uncollected* — a state a future rule can still address. Migration `116_subscription_status_completed` adds the enum value (its own migration, PG 55P04); the webhook now splits the two events onto **both** columns (`Subscription.status` and `Retailer.plan_status` — one enum, two columns, so fixing only one would have moved the collapse rather than removed it); `cancelled_at` is deliberately left null for a completion so the audit trail keeps the distinction the original bug destroyed; T5 keys on `CANCELLED` only, so a completed term falls through to the inert `NO_ACTIVE_SUBSCRIPTION` wait with nothing taken back; and the repeated `=== 'CANCELLED'` reads collapsed into a shared `isPlanEnded()` that treats both ended states alike while deliberately **excluding `PAST_DUE`** (dunning is recoverable — this entry's own T5 precedent). The "both events" test pair is the point: the webhook tests assert `COMPLETED` **and** that `cancelled` still writes `CANCELLED`, because a one-sided fix would have satisfied the bug report while relocating the collapse. **Reachability, stated honestly:** subscriptions are created with `total_count: 120`, so `subscription.completed` fires roughly a decade out — this is a correctness fix with a money reader, not a live-flow bug, and it should not be expected to fire before it is exercised by hand.
- **Symptom:** a retailer whose Razorpay subscription ran to its natural end (`subscription.completed`) is indistinguishable in the database from one who cancelled early. Both get `status: 'CANCELLED'`, `cancelled_at: <now>`, `Retailer.plan_status: 'CANCELLED'` and `razorpay_subscription_id: null`. Any consumer keying on `CANCELLED` — today, T5's churn clawback; tomorrow, churn analytics, win-back campaigns, or retention reporting — silently counts a successful completion as a loss.
- **Root cause:** **two distinct lifecycle events share one enum value because the enum has no room for the distinction.** `SubscriptionStatus` is `TRIAL | ACTIVE | PAST_DUE | CANCELLED` — there is no `COMPLETED`/`EXPIRED`, so the webhook had only two options (map a completion to `CANCELLED`, or invent a status) and chose the former. Every consumer downstream then inherits the ambiguity for free, because there is no column that preserves which event actually arrived. The collapse also overwrites the audit trail in the same statement: a completed subscription gets `cancelled_at` stamped and its `razorpay_subscription_id` nulled, so the original subscription cannot even be looked up afterwards to reconstruct what happened.
- **Why it was invisible:** nothing in the repo reads `CANCELLED` for a consequential decision until T5. The billing screens show a plan state, and "cancelled" reads as correct to a human either way — the information that distinguishes the two events is destroyed at write time, so no later query can recover it, and no test asserts the mapping's fidelity.
- **Why the T5 decision is nevertheless CORRECT (⚠️ revised 2026-09-24 — see "Resolution": the owner ruled completion is *not* churn; this argument is kept as the finding-time reading, not as current policy):** the qualify gate is *sustained paid **and** active through the window*, and a subscription that has completed is not active. Whether a retailer finished their term or left early, at the moment the conversion comes due they are not a paying, active customer — so `CLAWED_BACK` is the right outcome under the spec's rule. The defect is the **lost distinction**, not a wrong payout. Stated explicitly so this is not fixed "because the numbers are wrong" — they are not.
- **Why deferred:** the fix is a schema change (`COMPLETED` in the enum, or a `cancellation_reason` / `ended_reason` column) plus a webhook mapping change plus a backfill — i.e. it touches billing, which is the revenue path. Doing it silently from inside T5 would be a large, unrequested change to money-moving code under a task about referrals. RC-027's lesson applies in the opposite direction here: the engine string was fixed because it produced a **wrong image**; this one produces a **right decision from an ambiguous row**, so it is recorded and left for an owner decision.
- **Proof:** `apps/api/src/jobs/referral-qualify.test.ts` pins the consuming behaviour — "claws back a store that paid and then cancelled inside the window" asserts `CLAW_BACK / REFERRED_CHURNED_AFTER_PAYMENT`, and "qualifies when an ACTIVE subscription sits alongside an older cancellation" asserts that a mere historical cancellation does not claw back. Both are asserted by name so a future change to the mapping has to confront these tests rather than quietly alter a payout. **Added 2026-09-24 (the fix):** `apps/api/src/jobs/referral-qualify.test.ts` now also pins *"does NOT claw back a store whose paid term COMPLETED"* → `WAIT / NO_ACTIVE_SUBSCRIPTION` (falsified: adding `'COMPLETED'` to the `.some()` branch fails it) plus *"still claws back when a CANCELLED row sits alongside a later COMPLETED one"* — the 4.2 ruling's edge case, decided rather than inherited, **pinned by test so the reading is visible to whoever revisits it**. `apps/api/src/routes/billing.test.ts` gained the two webhook tests (a completion writes `COMPLETED` to both columns with no `cancelled_at`; a cancellation still writes `CANCELLED`), falsified by restoring the pre-fix mapping, which fails the completion arm — the webhook had **no test file at all** before this, which is why the original collapse survived review.
- **Prevention lesson:** **collapsing two states into one enum value destroys information at write time, and the loss only becomes visible at the first consumer that must act differently on the two.** When a webhook maps external event names onto an internal enum, the mapping is a *lossy* transformation and deserves the same suspicion as a unit conversion: ask what distinguishes the collapsed inputs and who will later need that distinction. Second-order rule this adds: **a job that makes a money decision from a status column should assert which source events can produce that status**, not merely that the status is handled — T5's tests do the latter, and this entry is the reminder that the former is still unverified.

## RC-032 — A library that throws on purpose was wired into a route whose own comment promised it could not fail, with no catch at the boundary — so an unapplied migration would 500 the onboarding save

- **Component:** `apps/api/src/routes/retailers/retailers-profile.ts` (`PUT /me`, the T4 capture call site) · `apps/api/src/lib/referral-conversions.ts` (the deliberate throw) · `packages/db/prisma/migrations/109_referral_program` (the dependency)
- **Commit:** found 2026-09-22 while building T4; fixed before the task's commit — the code is in `apps/api/src/routes/retailers/retailers-profile.ts` with the guard in `apps/api/src/routes/retailers/retailers-profile.test.ts`
- **Symptom (had it shipped):** `PUT /v1/retailers/me` returns **500** for any retailer whose payload contains a non-empty `referral_code`, for as long as migrations 109/110/111 are unapplied — i.e. **onboarding is blocked** for exactly the users who tried to enter a referral code, which is the behaviour the affiliate program exists to encourage. Nothing in the repo reports it: the route's own comment states the opposite, so a reviewer reads the promise rather than the behaviour.
- **Root cause:** **two independently-correct decisions that compose into a defect, because the only place the contradiction could be resolved had no code in it.**
  1. `applyReferralCapture()` **throws** on a database error, and its header says so deliberately: a capture that failed silently is a shop that was referred and a referrer who is never paid.
  2. The route was written non-fatal for referral problems, following the *same handler's* existing F-018 precedent ("silently ignored if invalid/blank"), and **documented that as a guarantee in a comment**. But the call site was a bare `await` — the comment asserted a contract that no `try`/`catch` implemented. A documented invariant with nothing enforcing it is a description of intent, not of behaviour.
  3. The trigger is a **deployment-order window the code cannot see**: migrations are applied by hand from the admin dashboard, while code deploys automatically from a push to `main`. Between those two events, `prisma.referralCode` typechecks (the schema declares the table) and every test with a mocked client passes, while the real database has no such table. No type, lint rule or test in this repo has an opinion on that gap.
- **Why it was invisible:** the 500 lands on the *profile save*, so it presents as a profile-validation bug rather than as a missing table. And the failure only occurs on a non-empty code — an empty or absent field short-circuits before any query — so a smoke test that saves a profile without a code is green.
- **Fix:** the call site catches, logs the underlying error through `request.log.error`, and reports `referral: { status: 'CAPTURE_FAILED' }` as data. Both halves of the requirement hold at once: the save cannot fail, and the failure is not swallowed. `ReferralCaptureReport` was added as the caller-facing type precisely so the next consumer (T5's qualify gate) sees that the caller's outcome set is one member wider than the library's return set, instead of re-deriving it.
- **Proof:** `apps/api/src/routes/retailers/retailers-profile.test.ts` — with the lookup rejecting, the response is **200**, the row is actually written (`retailer.update` called once), and `referral` is `{ status: 'CAPTURE_FAILED' }`; a second test asserts the log carries the underlying error's **message**, because "non-fatal" must not mean "invisible". **Falsified:** restoring `throw error` inside the catch fails both with `expected 500 to be 200`.
- **Prevention lesson:** **a library's deliberate throw and a caller's non-fatal contract are a contradiction that only the call site can resolve — and a comment asserting the contract is not the contract.** When the dependency of a captured value is a migration someone else applies by hand, the optional field must not be able to break the core flow, and the failure must still be reported: swallowing it converts a visible outage into an invisible lost referral, which is the worse of the two. Same shape as RC-027 and RC-029 — a fix (or a feature) whose real precondition is data or config that nothing verifies. Second-order rule this adds: **when a route comment claims a guarantee, the test file must be what asserts it.** Re-read every "never fails" / "always" comment in a file you are editing and check a `catch` is actually there.

## RC-031 — The affiliate/staff code separation rested on one character, and the guard protecting it checked only that a hyphen was *present* — so relaxing the pattern silently merged the two namespaces

- **Component:** `apps/api/src/lib/referral-codes.ts` (`isReservedForAffiliateNamespace`) · `apps/api/src/routes/team/team-members.ts` (the hand-editable F-018 field it guards)
- **Commit:** found 2026-09-22 by falsifying this feature's own new guard during T3; fixed the same session — `40e7d53b` (`feat(referrals): T3 affiliate code namespace + mint endpoint (RC-031)`)
- **Symptom:** nothing observable. The guard passed, the tests were green, and the failure it exists to prevent was reachable: a staff member typing `KAN7F3QMP` into the F-018 field would have it accepted, while `classifyReferralCode()` sent that same string to the **affiliate** ledger. One string, two ledgers, one of them paying the wrong actor.
- **Root cause:** the guard tested `value.includes('-')` — the presence of the separator — while the *requirement* is that the two namespaces be **disjoint**. Those are the same test only as long as the affiliate pattern keeps the hyphen mandatory. Relaxing it to `-?` (the kind of one-character change a later author makes to be "lenient about input") left `KAN7F3QMP` matching the affiliate pattern **and** the staff pattern, and the guard still passed because the string merely had to *contain* a hyphen somewhere. **The whole separation rested on one character, and nothing asserted that character was required.**
- **Why falsification found it and the test suite did not:** the existing tests all used well-formed codes, so they exercised the pattern in the one shape where presence and disjointness agree. Making the hyphen optional failed **nothing** — the guard was green for the wrong reason, which is the only way an invariant can be missing without any test noticing.
- **Fix:** the guard is now broader than the pattern it protects, in both directions — **any** hyphen is refused (a hand-typed `KAN-typo` is not a valid affiliate code either, but it is indistinguishable from the affiliate prefix to a human reading the column), **and** the hyphen-dropped shape is refused. A test asserts a hyphen-stripped minted code classifies **neither** `AFFILIATE` nor `STAFF`, so a future relaxation of the pattern fails the suite instead of the ledger. `KAN001` still classifies `STAFF` (the affiliate alphabet omits `0`/`1`/`I`/`L`/`O`), which is why reserving the `KAN` prefix outright was rejected — it would have broken the existing F-018 fixture for no gain.
- **Proof:** deliberately relaxing `AFFILIATE_CODE_PATTERN` to make the hyphen optional now fails the disjointness test with the offending code named. This was the **third** guard in the session that only held once it was deliberately broken.
- **Prevention lesson:** **when a guard's job is to keep two sets apart, assert the sets are disjoint — do not assert a proxy for it.** A test that the separator exists is not a test that the namespaces cannot overlap; the difference is invisible until the pattern changes, and by then the guard is the reason nobody looked. The generalisable habit: after writing any guard, break the thing it protects in the smallest plausible way and confirm the guard fails. If breaking it fails nothing, the guard is decorative.
