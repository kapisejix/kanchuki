1. What is actually happening right now

1.1 The error is not a bug — it's a dead integration

packages/ai/src/snappyit.ts calls https://snappyit.ai/api/v1/ghost-mannequin. The comment already sitting in that file, written by whoever built it, says:

"Confirmed: snappyit.ai domain (moved from snappyit.app in 2026). The /api/v1/ghost-mannequin path is inferred from industry patterns; actual endpoint to be confirmed during integration."

That is an admission the endpoint was guessed, never verified against a real API. This session's research confirms why it was never confirmed: Snappyit does not have a public developer API.

Verified 2026-08-06: Snappyit's own pricing page sells only consumer credit packs ($6.90–$48.90/mo, 100–1,150 credits) through a web dashboard. No mention of "API," API keys, or programmatic/batch access anywhere on the page. There is no developer portal. A search for one surfaces an unrelated company (snappy.com, a business gift-card API) that happens to share a similar name.

So the honest state of F-001e as shipped: it is wired to call an endpoint that was never confirmed to exist, on a vendor that — as far as this research can find — has no API to call in the first place. SNAPPYIT_API_KEY was never "missing configuration" in the normal sense; there was never a key to get. Setting an env var would not fix this — the URL it posts to is a guess.

This is on the project, not on you. F-001e was written into CLAUDE.md months ago as "via Snappyit API (planned)" and nobody validated that claim before code was built against it. You're not moving in circles by changing your mind — the plan itself was built on an unverified premise.

2. Why V-Tone doesn't cover this either

V-Tone is a virtual try-on engine: garment photo + a photo of a person/model → the garment shown worn by that person. Ghost mannequin is the opposite kind of shot — the garment shown as if worn by nobody visible at all. V-Tone has no invisible-mannequin mode.

Measured live, 2026-08-06: a real end-to-end V-Tone run on the CX43 took 32.3 minutes for one image (30 diffusion timesteps, CPU-only, no GPU on this box). It's also single-request-blocking — a second job waits for the first. For a catalog feature meant to run per-SKU across hundreds of products, that's not usable — confirming "vtone (which is not usable)" is correct, for this job.

3. Deep research: no-API self-hosted options that actually work

There is a real, permissively-licensed, self-hostable class of tool for this — split into three honest quality tiers rather than just tool names.

TierTechniqueNeedsAI required?
A — True ghost mannequin
(studio standard)		 Garment shot twice — once on a mannequin, once with the interior neck/collar photographed after slightly lifting the garment. The two are layered so the interior shows real fabric, not a guess. 2 real photos per SKU + compositing script No — pure alpha-masking & layering
B — Single-photo AI approximation One photo → background/mannequin removed → hollow interior (neckline, cuffs, waist) inpainted with plausible fabric-colored shading. 1 photo + a small inpainting model Yes, but CPU-feasible (§3.2)
C — Full AI reconstruction One photo of a worn garment → a diffusion model hallucinates a canonical "flat"/ghost view from a single view (2024–2025 "Virtual Try-Off" research, e.g. TryOffDiff, CVPR'25). 1 photo + a full diffusion pipeline Yes — same model class as V-Tone, same CPU cost problem

Snappyit / Photoroom / Pixelcut sell you Tier B, wrapped in a UI, charged per credit. If they were running Tier-C-heavy compute, a $6.90/mo plan with instant turnaround wouldn't be economical for them either.

3.2 Tier B is the realistic, CPU-only, no-API answer

IOPaint (formerly "lama-cleaner"), Apache 2.0, self-hosted, Python — github.com/Sanster/IOPaint. Packages the LaMa inpainting model (a small CNN, not a diffusion model).

  • License: Apache 2.0 — same free-to-self-host category as V-Tone and rembg, already proven acceptable in this project.
  • CPU speed: independently benchmarked at ~25 seconds/image on CPU (HD images, 7–10% masked). A completely different order of magnitude from the 30-minute diffusion runs — LaMa is a small CNN, not a multi-step diffusion sampler.
  • Pipeline it would need:
    1. rembg (already in use) — cut the garment out from its background/mannequin.
    2. A mask over the neckline/sleeve-opening/waist areas — approximated heuristically (silhouette minus a shrunk interior region), or reused per garment shape since most kurtis/suits/sarees in one category share similar neckline geometry.
    3. Feed cutout + mask to IOPaint's LaMa model → it fills the hollow area with plausible fabric texture.
    4. Composite onto a backdrop exactly like batch-clean-photos.py already does today.
  • Resource fit for CX43 (8 shared vCPU, 16GB RAM, no GPU, €12/mo — the box already running V-Tone): trivially fits. LaMa's published benchmark hardware is far less than a CX43. This is the one AI option in this document proportionate to the hardware already bought.
Honest quality ceiling: this is an approximation, not a true 3D reconstruction — it won't recreate exact fabric folds the way a real second photo (Tier A) or a heavier diffusion model (Tier C) would. For catalog thumbnails at typical e-commerce size this is plausibly good enough — it's functionally the same tier of quality the $7–35/mo SaaS tools were about to be paid for anyway.

3.3 Tier C (diffusion-based) — researched, not recommended

Academic work (TryOffDiff, CVPR 2025 — github.com/rizavelioglu/tryoffdiff, license: SSPL) reconstructs a garment's canonical shape from a single worn photo using Stable Diffusion as a base — the closest thing to "real AI" ghost-mannequin generation.

Same wall already hit and measured: Stable Diffusion-class inpainting on CPU only, independently benchmarked at ~20–22 minutes/image on hardware comparable to the CX43's shared vCPUs. Swapping "try-on" for "try-off" doesn't change the underlying cost — diffusion sampling is what's slow on CPU, not the specific task. Do not build this tier without adding a GPU.

5. Straight answer: what's the best fit

  1. Stop pretending Snappyit works. It's not a configuration gap — the integration targets a product with no API to integrate with. Recommend removing the "ghost mannequin" checkbox from the admin photo-cleanup page and the snappyit.ts/ghost-mannequin.ts files until a real path is chosen; leaving them produces this exact error forever.
  2. The proportionate, no-API, CPU-only answer is IOPaint/LaMa (Tier B). Runs comfortably on the CX43 already paid for, at ~25 sec/image — fast enough for real batch catalog use, unlike V-Tone or any diffusion route. Quality is an approximation of ghost mannequin, the same tier the cheap SaaS tools sell.
  3. If retailers take one extra photo per new design (the interior-neckline shot), Tier A gives the real professional-grade result other ghost-mannequin services sell by hand — zero ongoing compute cost, zero model-quality risk, at the cost of one extra shot per design (matches F-001e's existing "unpack once per design" premise).
  4. Full diffusion-quality reconstruction (Tier C) needs a GPU to be usable — the exact tradeoff already declined once for V-Tone (GPU ≈€184/mo vs €12/mo CPU box). Nothing found here changes that calculus for ghost mannequin specifically.
