## Findings

| ID | Sev | file:line | Issue | Proof | Fix |
| --- | --- | --- | --- | --- | --- |
| F1 | P1 (P0 once add-on packs are active) | `plugins/auth.ts:468-483` | `GET /v1/billing/addon-callback` is the `callback_url` of the Razorpay Payment Link (`billing-addons.ts:130`). Razorpay sends the buyer's **browser** there with no `Authorization` header, but the global `preHandler` skips only `/v1/billing/webhook`, `/v1/public`, `/v1/admin`, `/v1/team`, `/v1/auth`, `/v1/try-on/remote`. So the callback answers `401 Missing Bearer token` and a paid add-on is never credited (the purchase stays PENDING). The route's tests stub auth with a fake hook (`billing-addons.test.ts:69-71`), so none of them see this. The catalog-upload payment callback sits under `/v1/public` and is not affected. Per CLAUDE.md add-on packs are inactive until the owner creates them, which is why this has not surfaced. | Proof test with the real `authPlugin`: `CALLBACK_STATUS 401 {"error":{"code":"UNAUTHORIZED","message":"Missing Bearer token","status":401}}  WEBHOOK_STATUS 200`. | Add the callback path to the skip list (the handler verifies the Razorpay signature itself) and a regression test that runs the real `authPlugin`. Diff below. |
| F2 | P1 (PLAUSIBLE) | `routes/billing/billing-webhook.ts` (replay guard), `routes/webhooks/razorpayx-payout.ts:56-62` | Webhooks older than 300 s are rejected with 401 `STALE_EVENT`. Razorpay delivers at-least-once and retries failed deliveries for hours with `created_at` unchanged. If the first delivery of `subscription.charged` hits a 500 (DB blip, deploy), every retry after 5 minutes is also rejected, so a paying retailer is never activated. The handler is already idempotent on `razorpay_payment_id`, so the age check is not what prevents double processing. I did not verify Razorpay's retry window against live traffic. | Quote: `Math.abs(Date.now() / 1000 - event.created_at) > WEBHOOK_MAX_AGE_SECONDS` returns 401. The payout webhook has a reconciliation pass; I found none for the subscription webhook. | Replace the age rule with event-id dedupe (`x-razorpay-event-id`, stored for N days), or widen the window for events that are idempotent by id. Owner decision (replay of an old `cancelled`/`activated` was the reason for the rule). |
| F3 | P2 | `routes/billing/billing-helpers.ts:246-253` (used by 3 webhook plugins) | `captureRawBody` reads the whole request stream into memory in a `preParsing` hook, **before** Fastify enforces `bodyLimit` and before the signature check, on unauthenticated routes (`/v1/billing/webhook`, `/v1/public/webhooks/razorpayx-payout`, `/v1/public/webhooks/whatsapp-catalog`). A client can make the process buffer a body of any size for a 413. Limited by the 200/min IP limit and any proxy cap; Railway memory is tight. | Proof test: `bodyLimit` 1 MiB, 8 MiB body: `STATUS 413 BUFFERED_BYTES 8388616 LIMIT 1048576`. | Count bytes in the loop and destroy the stream past 1 MiB, returning 413. Diff below. |
| F4 | P2 (not verified) | `index.ts:70,143` | `trustProxy: true` in production with `keyGenerator: request.ip`. With `true`, Fastify trusts every hop of `X-Forwarded-For`, so if the edge **appends** rather than replaces the header, a client can pick its own IP per request and bypass every per-IP limit (OTP send, admin login, upload URLs, webhooks). The comment at `index.ts:137-141` says client headers are never trusted. Whether Railway's edge overwrites the header was not verified (needs a staging request). | Config quotes only. | On staging, send `X-Forwarded-For: 1.2.3.4` and read the logged `request.ip`. If spoofable, set `trustProxy` to the hop count (e.g. `1`). |
| F5 | P2 | `routes/billing/billing-addons.ts:393-446` | `POST /billing/create-order` creates a Razorpay order of any amount (100 to 1,000,000 paise) for any authenticated owner, and `POST /billing/verify-payment` returns `verified: true` for a valid signature but fulfils nothing (its own comment says fulfilment "happens separately"). No client calls either. Dead surface that looks like it grants something. | `grep -rE "create-order\|verify-payment\|createOrder\|verifyPayment"` over `apps/mobile` and `apps/web/src`: no matches. | Delete both routes, or tie them to a purchase row. |
